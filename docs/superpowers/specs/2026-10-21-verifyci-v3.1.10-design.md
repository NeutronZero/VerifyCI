## 0. Document status, evidence boundary, and change log

### 0.1 Status and evidence boundary

This document is a design specification. It defines the product contract, boundaries,
failure semantics, deployment requirements, and release gates for VerifyCI v3.1. It is not
implementation evidence.

Freezing this design does **not** establish that latency, precision, recall, frontend
fidelity, cache parity, conclusive-rate, or performance targets have been met. Those claims
are established only by release-validation artifacts:

- per-check corpus reports against frozen, hand-authored, partly independently labelled cases;
- mined real-world corpus reports (adjudicated precision and conclusive rate);
- frontend conformance and differential-fidelity reports;
- deterministic evidence-bundle, cache-parity, and uncached-audit runs;
- cold/warm latency and memory measurements on the reference workload;
- the published `CheckSpec` manifest and its hashes.

Until those artifacts exist and are reviewed, every capability in this document is a design
target, not a measured result. Numeric thresholds marked *initial* are calibration starting
points; changing them requires a specification update.

## 1. Product contract

VerifyCI v3.1 is a local-first, deterministic **pre-merge CI gate for AI-authored diffs**.
It verifies the diff between the merge base and the pull-request head against the policy
of the target branch, then emits:

- a structured verdict and exit code;
- a canonical, reproducible evidence bundle;
- SARIF v2.1.0 for CI and code-scanning surfaces.

The only supported surfaces are a CLI and a composite GitHub Action. There is no daemon, server, database, or model call, and the verification core has no network dependency (§1.4).

### 1.1 Defect families

The gate declares five defect families:

1. **Semantic regressions** in modified functions: removed or weakened protected guards,
   inverted guards, swapped argument/return bindings, and removed protected error paths.
2. **Provenance and grounding failures**: integrity failures such as inconsistent Git
   identity (`ERROR`), unmapped changes (`INCONCLUSIVE` when a symbol rule needs the mapping),
   and changes prohibited by an explicit `deny_changes` rule (`FAIL`).
3. **Security regressions**: validated secrets, taint flows to dangerous sinks, and exact
   policy-forbidden calls.
4. **Caller and contract breakage**: incompatible signatures, exports, visibility, async
   status, or call sites.
5. **Unsafe deletion**: removed symbols that remain reachable, dangling references, or
   proven dynamic references to removed symbols.

A release manifest (§11.8) states which families are **blocking**, which are **shadow**
(run and reported, never affecting the verdict), and which are **not shipped**. v3.1.0 targets
blocking grounding, deletion, contract, and security, with semantic in shadow (§16).

### 1.2 What VerifyCI does not claim

VerifyCI does not prove general program correctness, whole-program equivalence, or full
language semantics. It does not execute repository code. It does not determine whether a
diff is "good"; it establishes whether a declared defect was found with evidence within a
declared scope. It does not verify the interaction between the PR and changes that landed on
the target branch after the merge base (§8.2) unless run on a merge candidate.

### 1.3 The PASS contract

The following text is normative and must appear in the README, the specification, and the
SARIF `properties`, with the bracketed parts filled from the release manifest and the bundle:

> PASS means every applicable blocking check in this release completed with COMPLETE
> coverage over its declared scope and no unwaived declared defect was established. PASS
> covers only the defect families listed as blocking in the release manifest [list]; families
> that are shadow or not shipped [list] were not enforced. Scope excluded by reviewed coverage
> acceptances [count, ids] is listed in the evidence bundle. PASS is not a claim that the code
> is correct or that the diff is safe in general. The evidence bundle states what was checked,
> the applicable assumptions, the excluded scope, accepted gaps, and any waived findings.

### 1.4 Execution boundary: Action bootstrap versus verification core

The product runs in two phases with different network properties.

| Phase | Network | Responsibilities |
|---|---|---|
| **Action bootstrap** | Enabled; outside the core | Checkout; fetching the target tip, head, and sufficient history; restoring cache artifacts; provisioning the pinned toolchain; after the core exits, uploading SARIF or summaries. It makes no verdict decisions. It may pass the fetch time to the core as informational metadata (envelope only). |
| **Verification core** (`vc gate`) | None | Everything from Stage [0] onward. Reads only pinned Git objects in the local repository, the target-base policy, the release manifest, and the local cache. No sockets, no fetch (including lazy fetch), no model calls, no repository-code execution. |

Everything the core needs must be present locally before it starts. A missing object is
`missing_git_object`, never a fetch. The core's offline property is enforced by
`GIT_NO_LAZY_FETCH`, workers spawned without network access (§13.4), and an end-to-end test
that runs the core with networking denied. Wherever this document says the gate or a check
has "no network access", it refers to the verification core.

## 2. Goals and non-goals

### 2.1 Goals

- Run on every pull request without becoming a CI bottleneck: p95 $\le 10$ seconds warm
  and $\le 60$ seconds cold on a 100k LOC reference repository.
- Verify only changed functions and the affected caller/reference closure.
- Require no persistent database and no ingest step for a correct verdict.
- Make every blocking decision reproducible, evidence-backed, and fail-closed.
- Treat unsupported semantics and incomplete candidate discovery as incomplete coverage,
  never as PASS — while giving repositories a reviewed, expiring way to declare known gaps so
  that PASS remains reachable.
- Resist being disabled or steered by the PR it verifies.
- Support Python and TypeScript/JavaScript as first-class languages.
- Keep the trusted computing base and dependency surface small.
- Ship incrementally: each check enters enforcement only at the maturity its evidence supports.

### 2.2 Non-goals for v3.x

- General behavioral equivalence or formal soundness for all programs.
- Full-repository semantic indexing or a code-property-graph database.
- LLM judges, conformal prediction, retrieval, reranking, or auto-repair.
- FastMCP daemons, agent servers, or long-lived processes.
- DuckDB, egglog, RaBitQ, WASM plugins, DSSE, in-toto, gittuf, or a hash-chained ledger.
- Executing repository code, including during witness validation.
- Patch-file input mode. v3.x verifies commit ranges only.
- Live (networked) secret verification.
- Full first-class semantics for Go, Rust, C/C++, JVM, or .NET languages.
- Repository-specific checker code or a rule DSL.
- Authenticating human identity for waivers or acceptances (delegated to the target branch's
  review process).
- Enforcing branch protection or rulesets from inside the gate (§8.6 states these as adopter
  requirements; the gate can only check what it can read from Git).

## 3. Normative invariants

1. No PASS with incomplete relevant coverage. Gaps covered by a valid coverage acceptance are
   removed from relevant scope, recorded, and listed in the PASS text; they are never silent.
2. No blocking finding without validated evidence of its declared kind.
3. Advisory and shadow check results — findings, outcomes, coverage, and faults — never change the verdict or exit code; aggregation considers blocking checks only.
4. No persistent state is required for correctness.
5. Completed executions with identical logical inputs (including `as_of_date`), policy,
   toolchain, deterministic analysis budgets, release-pinned cache-sampling policy, and either
   no cache or the same valid/authentic cache contents produce byte-identical canonical payloads.
   A deterministically sampled cache-integrity mismatch intentionally produces `ERROR`; this
   integrity-failure path is tested separately from cached/uncached parity. Resource exhaustion
   may produce `INCONCLUSIVE` and must never produce PASS.
6. Analysis work is bounded; exhaustion cannot produce PASS.
7. Policy is validated declarative data and never executes code.
8. Unsupported languages never receive unsubstantiated semantic PASS results.
9. Cache is optional acceleration, lives outside the PR-controlled working tree, and cannot suppress a finding: in CI it is HMAC-authenticated under a protected key or disabled; an unauthenticated entry never influences an authoritative verdict; PR-event runs never write it; deterministic per-entry sampled recomputation and scheduled uncached audits detect cache faults (§14).
10. Git objects, read through a hardened plumbing interface, are the sole authority for
    merge-base, target-base, head, and file contents; the working tree is never authoritative.
11. Every check in the release manifest (blocking or shadow) produces a `CheckResult`,
    including not-executed, not-applicable, and error results.
12. Checks never call Git, read the working tree, access the network, or share mutable
    semantic state.
13. The policy used for a run is loaded from the target-base commit, never from the head (with the sole exception of the fail-closed onboarding bootstrap when the target base has no policy file and the PR adds a valid one, which always yields `REVIEW` under §8.3).
14. A validated finding is preserved when its check also faults; the check outcome is `ERROR`
    and the aggregate verdict is `ERROR`.
15. A release manifest lists each check at a declared maturity and exists only when each listed
    check satisfies the evidence requirements of that maturity and all invariant, fidelity,
    and performance gates pass.
16. A change to a gate-controlling path (§8.5) can never produce an unreviewed `PASS`.
17. The verdict never hides a blocking finding: whenever any unwaived blocking finding exists,
    `verdict.blocking_findings_present` is `true` regardless of aggregate status.
18. The verification core performs no network access; all network activity belongs to the Action bootstrap (§1.4).

| Coverage gap | A relevant entity, reference, or path a check could not resolve, tagged with a reason code. |

| Toolchain fingerprint | Versions and configuration of the interpreter, frontends, analyzers, solver, canonicalizer, and pinned Git invocation settings that can affect results. |
| Qualified name | `module:qualname` identity defined in §8.4.1. |

## 5. Verdict algebra

### 5.1 Verdicts and exit codes

Aggregation is defined over checks with tier `blocking` only. Shadow and advisory results never enter the conditions below (§5.2).

| Verdict | Exit | Condition |
|---|---:|---|
| `PASS` | 0 | Every blocking check has `COMPLETE` coverage (after accepted gaps) and outcome `PASS`, `NOT_APPLICABLE`, or `FAIL` whose findings are all `WAIVED`; no unwaived blocking finding exists; no blocking check is `INCONCLUSIVE` or `ERROR`; no `REVIEW` condition exists. |
| `FAIL` | 1 | At least one independently validated, unwaived blocking finding exists, and no blocking check outcome is `ERROR`. Other checks may be incomplete. |
| `INCONCLUSIVE` | 2 | No unwaived blocking finding and no blocking `ERROR`, but at least one blocking check is `INCONCLUSIVE`, has `PARTIAL`/`UNKNOWN` coverage, or exhausted its deterministic budget/watchdog; or `target_drift` under `require_zero`. |
| `ERROR` | 3 | Invalid authoritative policy, invalid proposed policy, missing/corrupt required Git objects, manifest mismatch, invalid cache location, cache integrity mismatch, any blocking check outcome `ERROR`, internal fault, or invalid check result. |
| `REVIEW` | 4 | No higher-precedence condition, but a gate-integrity change, a PR-authored policy change (including onboarding bootstrap), an inactive authoritative waiver/acceptance (expired or not-yet-effective) that matches a current finding/gap, or an expired schema-valid waiver/acceptance left in a policy-changing PR requires designated review. |

Precedence: `ERROR > FAIL > INCONCLUSIVE > REVIEW > PASS`. The exit code is taken from the
winning verdict; exits 2 and 4 are distinct so automation can route "needs a human decision"
(4) separately from "analysis could not finish" (2).

**Proposed-entry date validation.** A waiver or coverage-acceptance record in a proposed policy
must have `created <= inputs.as_of_date` when it is newly added or any of its normalized canonical
record fields differ from the authoritative record with the same stable policy ID. The stable
policy ID and the exact normalized-record comparison are defined normatively in §8.4.3; this test
uses the complete record, not the waiver finding fingerprint. A record whose complete normalized
fields are unchanged from the authoritative policy may have a future `created` date: it remains
structurally valid but inactive until that date. Renaming a record's table key makes the old ID a
removal and the new ID a newly added record, so the proposed-entry date constraint applies to the
new record. Onboarding bootstrap has no authoritative records, so every proposed waiver/acceptance
is treated as newly added. This rule does not waive other schema checks, including required fields,
date parsing, `expires >= created`, or the 180-day acceptance lifetime limit.

### 5.2 Verdict rules

- A proven blocking defect establishes a blocking finding. Absent a higher-precedence
  `ERROR`, the aggregate verdict is `FAIL`, even when other relevant scope is unsupported or
  later exhausts its budget. Incompleteness never erases the finding.
- A check that establishes a finding and then faults records outcome `ERROR`, keeps the
  finding and its evidence in `findings[]`, and records the fault in `diagnostics[]`. The
  aggregate verdict is `ERROR`; the finding remains visible and blocking. Any check outcome
  `ERROR` outranks a `FAIL` elsewhere and is never hidden by it.
- **`ERROR` never masks a defect.** The bundle's `verdict` carries
  `blocking_findings_present` (true when any unwaived blocking finding exists anywhere,
  including under an `ERROR` check) and `fault_reason_codes[]`. Consumers (the Action summary,
  SARIF run properties) must surface both, so "infrastructure fault" and "real defect found,
  fault also occurred" are distinguishable. The exit code remains 3.
- A blocking check that has `PASS` with `PARTIAL` or `UNKNOWN` coverage is an invalid
  result; the orchestrator records aggregate `ERROR` with reason `invalid_check_result` and
  preserves any validated findings.
- A shadow/advisory check that emits an invalid result (including `PASS` with `PARTIAL` or
  `UNKNOWN` coverage, malformed fields, or an internal check-local fault) is recorded as an
  invalid advisory result plus a diagnostic. It does not enter verdict aggregation and cannot
  change the verdict or exit code. This isolation applies only to faults contained within that
  check; shared infrastructure failures in Git access, authoritative policy, manifest loading,
  orchestration, or canonical bundle serialization remain aggregate `ERROR`.
- `NOT_APPLICABLE` requires positive applicability evidence. It is never a substitute for
  unsupported analysis.
- Budget exhaustion, a timeout, or a watchdog interruption leaves coverage `PARTIAL` or
  `UNKNOWN` and is `INCONCLUSIVE` (`budget_exhausted` or `watchdog_interrupted`) when no
  finding is established. After a finding, the finding survives and the check outcome is
  `FAIL`. It is never `PASS` and never by itself evidence of a defect.
- **Shadow and advisory results never enter aggregation.** Any outcome of a shadow or advisory
  check — including `INCONCLUSIVE`, `ERROR`, `PARTIAL`/`UNKNOWN` coverage, and findings — is
  recorded in the bundle (tier `advisory`) and rendered in SARIF as notes or tool
  notifications. It cannot prevent `PASS`, cannot create `FAIL`, and cannot change the exit
  code. A fault *contained within* a shadow check's own execution (including a sandboxed
  worker crash) is a shadow diagnostic. A fault in shared infrastructure (Git access, policy,
  manifest, orchestrator, bundle serialization) is not contained in a check and remains
  `ERROR`. Shadow checks run after all blocking checks (§13.1).

### 5.3 Waivers

A waiver changes a finding's `disposition` from `OPEN` to `WAIVED`. It does not remove the
finding, the check result, or the witness. The check retains its highest-precedence outcome:
`FAIL` when the finding is the highest result, or `ERROR` when the check also faulted.
Aggregation asks whether any **unwaived** blocking finding remains, but an `ERROR` outcome
still outranks `FAIL`. Aggregate `PASS` is therefore possible with a `FAIL` check result only
when every blocking check has `COMPLETE` coverage and every blocking finding is `WAIVED`; a
check with outcome `ERROR` never permits `PASS`.

A waiver cannot override:

- `ERROR`;
- incomplete coverage or a `PARTIAL`/`UNKNOWN` check result (use a coverage acceptance, §6.6);
- budget or watchdog exhaustion;
- a `REVIEW` condition;
- missing evidence.

An inactive (expired or not-yet-effective) or fingerprint-mismatched waiver does not waive a finding. Missing, empty, wrongly
typed, or structurally invalid required fields are a policy validation `ERROR` (`invalid_policy`),
not a review-only condition (§8.4.3). A waiver is active only when $\text{created} \le \text{as\_of\_date} \le \text{expires}$ (§8.4.4). VerifyCI does not authenticate
the identity represented by `approved_by`; the required review process is responsible for that.

- If an inactive (expired or not-yet-effective) waiver in the authoritative policy **matches** a finding in the current run,
  the finding remains `OPEN` and `REVIEW` (`waiver_review`) is recorded alongside the unwaived
  `FAIL`. If a schema-valid proposed policy removes or validly renews that waiver with an active
  date range, the review reason for that entry becomes `policy_change_review`; the finding remains
  open in this run.
- An inactive waiver in the authoritative policy that does **not** match a finding does not block
  unrelated PRs; it is recorded as an advisory `stale_waiver_present` diagnostic. If the PR changes
  `.verifyci/policy.toml`, any expired waiver remaining in the proposed head policy yields `REVIEW`
  (`waiver_review`), whether or not it matches a finding in this run. The proposed-entry date
  constraint applies only to newly added or semantically modified records as defined in §5.1;
  unchanged future-dated authoritative records remain valid but inactive.
- The same proposed-policy rule applies to coverage acceptances: any expired acceptance left in a
  policy-changing PR yields `REVIEW` (`coverage_acceptance_review`), matched or unmatched. An
  inactive authoritative acceptance that matches a current coverage gap is ineffective and
  records that review reason; if it is unmatched on an unrelated PR, it is recorded as an advisory
  `stale_acceptance_present` diagnostic. The proposed-entry date constraint likewise applies only
  to newly added or semantically modified records. An unchanged future-dated authoritative
  acceptance remains valid but inactive.

Supersession is a relabelling among REVIEW reasons only. It never changes a finding's
`disposition` or a coverage gap's accepted status, never lifts a `FAIL` or an `INCONCLUSIVE`,
and applies only when no unwaived blocking finding and no unaccepted gap remains in the run
(§8.3.1). Missing or empty required authorization metadata is a schema error (`invalid_policy`),
not a review-only condition (§8.4.3).

### 5.4 Reachability of PASS

A gate that can never say PASS trains teams to bypass it. v3.1 therefore requires that every
`PARTIAL`/`UNKNOWN` cause arising from an *unmodelled but benign, policy-expressible construct*
has a declarative resolution path:

1. **Model it** (preferred): declare a decorator transparent or a call pure/sanitizing (§8.4).
2. **Accept it**: use a reviewed, expiring, scoped coverage acceptance where Appendix A marks the
   reason code acceptable (§6.6).
3. Otherwise the result stays `INCONCLUSIVE`.

This is not a promise that every coverage gap has a policy override. Evidence-alignment failures,
parse failures, budget exhaustion, unknown solver results, and other non-acceptable gaps must be
resolved by changing the code, the structural scope of the change, or the supported analyzer; they
must not be waived merely to make PASS reachable. In particular, `semantic_alignment_unresolved`
remains non-acceptable because an acceptance cannot manufacture a trustworthy base/head alignment.
Release validation measures the **conclusive rate** (share of mined PRs reaching `PASS` or `FAIL`)
so that unreachable PASS for ordinary policy-expressible benign cases is detected before release
(§15.4).

## 6. Coverage, check results, and evidence

### 6.1 Coverage definition

> COMPLETE coverage means that scope enumeration and candidate discovery are complete for
> the check's declared defect set within its explicitly supported subset; every relevant
> entity has the required capabilities, and every candidate has been proven, refuted, or
> otherwise accounted for under the check's evidence contract. Gaps removed by a valid
> coverage acceptance are not part of relevant scope and are listed as accepted gaps.

`COMPLETE` does not require general program equivalence or a formal soundness proof for every
analyzer. Each check must define:

- its supported syntax and facts;
- its relevant scope;
- its candidate-generation rules;
- how unsupported cases are identified and reported.

A candidate that is never discovered cannot be counted as resolved. Frozen corpora validate
these claims empirically; they do not establish soundness for unseen programs.

Operationally, `coverage = COMPLETE` requires both `scope_enumeration.complete = true` and
`candidate_discovery.complete = true`. If either is false, coverage is `PARTIAL` or `UNKNOWN`,
and the check cannot return `PASS`.

### 6.2 CheckResult

Every check in the manifest receives exactly one top-level record:

```text
CheckResult
  check_id
  check_version
  tier: blocking | advisory          # shadow checks are tier advisory
  maturity: shadow | provisional | stable
  outcome: PASS | FAIL | NOT_APPLICABLE | INCONCLUSIVE | ERROR
  coverage: COMPLETE | PARTIAL | UNKNOWN
  evaluated_scope
  scope_enumeration { method, version, complete }
  candidate_discovery { method, version, complete }
  applicability_evidence
  method
  method_version
  reason_codes[]       # check-level codes only: A.3 coverage-gap codes and A.1 fault codes
  coverage_gaps[]      # { reason_code (A.3), subject, accepted: bool, acceptance_id? }
  findings[]           # validated findings; allowed with FAIL or ERROR
  diagnostics[]        # fault detail, expected/actual IDs; required for ERROR
  sub_results[]        # security sub-analyses and other composite checks
  toolchain_fingerprint
```

`outcome` and `coverage` are independent. `FAIL` with `PARTIAL` or `UNKNOWN` coverage is valid
and blocking. `PASS` with anything other than `COMPLETE` is invalid. `NOT_APPLICABLE` requires
`COMPLETE` coverage of the applicability question.

`FAIL` requires at least one finding. `PASS`, `NOT_APPLICABLE`, and `INCONCLUSIVE` carry no
findings; a validated finding makes the outcome `FAIL` unless the check also faults, in which
case it is `ERROR`. `ERROR` requires at least one diagnostic or reason-code entry identifying
the fault, and may carry zero or more validated findings when findings and a fault coexist.
A validated finding is never discarded and never downgraded to `PASS` or `INCONCLUSIVE`.

A fault that prevents analysis of relevant scope must reduce coverage to `PARTIAL` or
`UNKNOWN`; `ERROR` does not by itself redefine coverage. A check may have `ERROR` with
`COMPLETE` coverage only when the fault does not prevent the declared relevant scope from
being analyzed, and it still never yields `PASS`.

Every check record is emitted even when:

- the check is not applicable, with applicability evidence;
- an upstream failure prevents execution, with `ERROR` and reason `not_executed`;
- the check itself faults, with `ERROR` and a contained reason code.

No successful or not-applicable result is fabricated to complete the bundle.

### 6.3 Findings

```text
Finding
  tier: blocking | advisory
  defect_id                    # one of the 16 declared IDs (§11)
  reason_code                  # required; the Appendix A.4 code bound 1-to-1 to defect_id
  defect_semantics_version
  subject { file, entity, base_span, head_span }
  premises { target_base_commit, merge_base_commit, head_commit,
             base_blob, head_blob, authoritative_policy_source,
             authoritative_policy_hash, check_version, toolchain_fingerprint }
  evidence:
    kind: solver | provenance | reference | call_site | taint_path | secret_validation
    payload
  witness_level: ir | source | none
  message
  remediation (optional)
  disposition: OPEN | WAIVED
```

`authoritative_policy_hash` is the digest of the effective policy that governed this run.
When a policy blob exists at `target_base_commit`, it equals the SHA-256 of that exact blob and
`authoritative_policy_source = target_blob`. During onboarding bootstrap, the source is
`builtin_bootstrap_v1` and the hash is the SHA-256 of the canonical JCS encoding of the
versioned built-in minimal policy object. The built-in object and its expected digest are pinned
in the release manifest; startup verifies that the embedded object hashes to that digest. The
bundle's `inputs.policy.authoritative_blob_hash` remains `null` in bootstrap mode because no
Git policy blob exists, while `inputs.policy.effective_policy_hash` and every finding premise's
`authoritative_policy_hash` carry the non-null effective-policy digest. The source discriminator
prevents the built-in policy digest from being mistaken for a target-branch blob hash.

A blocking finding requires validated evidence of its declared kind: a solver witness, exact
provenance, an exact reference, a call-site mismatch, a taint path, or an offline-validated
secret. The kind must be one of the allowed kind(s) for its `defect_id` in Appendix A.4;
contract tests validate `(defect_id, reason_code, evidence.kind)`. Heuristic suspicion cannot block. Secret evidence is redacted; it must be sufficient
to reproduce the finding without exposing the credential. A finding's canonical identity is
the waiver fingerprint defined in §8.4.3; it is stable across rebases and tool upgrades that
do not change defect meaning, and excludes line numbers.

**`reason_code` and the six code classes.** Every finding carries exactly one `reason_code`,
and the pair `(defect_id, reason_code)` must be a row of Appendix A.4; the mapping is a
bijection. A finding with a missing code or a pair that is not an A.4 row is an invalid check
result (`invalid_check_result`, §5.2). `reason_code` is a function of `defect_id`, so it is
not part of the waiver fingerprint (§8.4.3). The catalog has six classes, each with exactly
one home:

| Class | Appendix | Where recorded |
|---|---|---|
| Finding | A.4 | `Finding.reason_code`; copied into `verdict.reason_codes[]` while the finding is unwaived and blocking |
| Coverage gap | A.3 | `CheckResult.coverage_gaps[].reason_code` and `CheckResult.reason_codes[]` |
| Fault | A.1 | `CheckResult.diagnostics[]`, `CheckResult.reason_codes[]`, and `verdict.fault_reason_codes[]` |
| Review | A.2 | `verdict.reason_codes[]` |
| Diagnostic | A.5 | `CheckResult.diagnostics[]` only; never in `reason_codes[]` or the verdict |
| Run condition | A.6 | `verdict.reason_codes[]` when the condition changes the run verdict; input fields also record the underlying condition |

`CheckResult.reason_codes[]` never contains finding codes: one check can emit findings of
several types, so finding codes live on the findings. `verdict.reason_codes[]` is the sorted,
de-duplicated union of (i) `reason_code` of every unwaived blocking finding, (ii) the A.3
codes of unaccepted gaps on blocking checks, (iii) the A.2 codes recorded for the run, and (iv) active A.6 run-condition codes whose documented verdict effect applies.

### 6.4 Evidence bundle

The bundle has two layers:

**Payload** — deterministic and canonical (RFC 8785 JCS):

```text
schema
tool { name, version, toolchain_fingerprint }
inputs { target_ref, target_base_commit, merge_base_commit, head_commit,
         object_format, target_drift, as_of_date,
         policy { authoritative_blob_hash, authoritative_policy_source,
                  effective_policy_hash, pr_changed, proposed_blob_hash },
         gate_integrity { changed_paths[] },
         files[] { status, base_path, head_path, base_blob, head_blob, base_mode, head_mode } }
manifest { check_specs[], builtin_policy_hashes{ builtin_bootstrap_v1 }, manifest_hash,
          release_summary { blocking[], shadow[], not_shipped[],
                            maturity{ check_id: shadow|provisional|stable } } }
scope { per-check evaluated_scope }
check_results[]
findings[]
waivers[]
accepted_gaps[]
verdict { status, exit_code, blocking_findings_present, reason_codes[], fault_reason_codes[] }
assumptions[]
excluded_scope[] { kind, path?, symbol?, acceptance_id?, detail? }
```

**Envelope** — non-semantic metadata:

```text
payload_hash
generated_at
target_fetched_at
timings
environment
cache { mode, authoritative, stats, sampled_recomputations }
signature (optional)
```

Timestamps, durations, worker counts, cache state, and environment never enter the canonical
payload. Same logical inputs, policy, `as_of_date`, toolchain, and deterministic budgets $\Rightarrow$
byte-identical payload for completed executions.

In `release_summary`, `blocking[]` is exactly the set of checks at maturity `provisional` or
`stable`; `shadow[]` is the set at maturity `shadow`; `maturity{}` records every shipped
check's maturity; `not_shipped[]` lists registered checks absent from the manifest.

The bundle must contain a record for every check in the manifest, including `NOT_APPLICABLE`
decisions and the evidence supporting applicability. A bug in scope selection must not be
able to turn skipped analysis into PASS.

`excluded_scope[]` always includes, when applicable:

- `target_changes_since_merge_base` when `target_drift` is true — the interaction between the
  PR and target-branch changes that landed after the merge base was **not** verified;
- content behind LFS pointers and submodule contents;
- external consumers not declared public;
- any accepted gap (with its acceptance ID).

Findings preserved under an `ERROR` check result remain in `check_results[].findings[]` and
in the top-level `findings[]`; the fault appears in `diagnostics[]`, and the aggregate verdict
remains `ERROR`. Composite sub-results may repeat findings for attribution; the top-level
`findings[]` rollup is deduplicated by canonical finding identity.

SARIF is a derived rendering of the same result: one result per `Finding`, including findings
preserved under `ERROR`, waived findings marked suppressed, check failures as tool
notifications, and the aggregate verdict, `blocking_findings_present`, PASS text, release
summary, and accepted gaps in run properties. The canonical payload remains authoritative.

### 6.5 Witness trust boundary for semantic findings

A semantic blocking finding requires all three contracts:

1. **Solver witness** — an input/state assignment demonstrating divergence within the
   declared VFIR semantics.
2. **Replay validation** — the VFIR evaluator independently reproduces the solver's result.
3. **Frontend fidelity** — the source constructs used by the witness are covered by the
   frontend's conformance and differential-fidelity contract.

v3.x never executes repository code. Its semantic evidence is therefore labelled
`witness_level: ir`, not source-level replay. Source-level runtime replay is out of scope
because executing untrusted repository code violates the gate's security boundary.

Frontend fidelity is established at release time by trusted fixtures in VerifyCI's isolated
CI. A fidelity mismatch invalidates the affected frontend capability and prevents the
semantic check from being promoted to blocking.

### 6.6 Coverage acceptances

A coverage acceptance is authoritative-policy data that removes a bounded class of coverage
gaps from a check's relevant scope. It exists so that known, reviewed, benign unmodelled
constructs do not make PASS permanently unreachable.

Rules:

- An acceptance names a `check`, one `reason_code`, and a scope of `paths` globs and/or exact
  `symbols`; at least one is required. Path globs are normalized repository-relative patterns
  under the §8.4.1 matcher. Reject leading/trailing separators, empty path segments, `.` or `..`
  segments, and any pattern equivalent to the universal language over all normalized, non-empty
  repository-relative paths. Test the *union* of an acceptance's `paths` globs, not each pattern
  independently: `*`, `**`, `**/*`, `**/**`, normalized equivalents, and any set of patterns that
  collectively covers every path are invalid. Implement a bounded regular-language coverage check
  with deterministic complexity limits; if coverage cannot be decided within the limit, reject the
  acceptance as `invalid_policy` rather than guessing that its scope is bounded. Exact `symbols`
  do not make a universal path scope acceptable.
- Only reason codes marked **acceptable** in Appendix A may be accepted. Never acceptable:
  budget/watchdog exhaustion, `solver_unknown`, `parse_error`, `parse_resource_limit`,
  `secret_candidate_ambiguous`, `taint_path_unresolved`, anything that is an `ERROR`, and
  anything that is a finding.
- Each acceptance has non-empty `reason` and `approved_by`, `created` (ISO date), and `expires`
  (ISO date). Missing, empty, wrongly typed, or structurally malformed required fields yield
  `ERROR` (`invalid_policy`) in authoritative and proposed policies. The validator rejects as
  `invalid_policy` any acceptance where `expires < created` or `expires - created > 180` days.
  The proposed-policy `created <= as_of_date` constraint applies only to an acceptance newly added
  or whose complete normalized record differs from the authoritative record with the same stable
  policy ID, as defined in §8.4.3 and applied in §5.1. Compare all normalized schema fields, including
  `created`, `expires`, `approved_by`, `reason`, and scope; do not use a waiver finding fingerprint as
  record equality. An unchanged authoritative entry copied into a proposed policy may be future-dated;
  it remains structurally valid but inactive before its `created` date. For onboarding bootstrap, where
  no authoritative policy exists, every proposed acceptance is treated as new. Renaming its table key
  is removal plus addition and applies the proposed-entry date constraint to the new record. Expiry is evaluated
  as a lifecycle/review condition rather than a schema error. A structurally valid but expired
  acceptance is ineffective and, if left in a policy-changing proposed policy, yields
  `coverage_acceptance_review` even when it matches no current gap. The 180-day ceiling remains
  invariant under historical replay runs while preventing long-lived acceptances from being authored.
- A **valid active** acceptance applies to a gap iff check, reason code, and scope all match. A
  matching gap is recorded in `coverage_gaps[]` with `accepted: true`, listed in `accepted_gaps[]`
  and `excluded_scope[]`, and does not reduce coverage. An inactive acceptance (`as_of_date <
  created` or `as_of_date > expires`) never receives `accepted: true` and never removes a gap from
  relevant scope. An acceptance never suppresses a validated finding and never converts an `ERROR`
  into anything else.
- If a current coverage gap matches an inactive authoritative acceptance (expired or
  not-yet-effective), coverage remains reduced (`PARTIAL`/`UNKNOWN`) and
  `coverage_acceptance_review` is recorded alongside the resulting `INCONCLUSIVE` outcome. A
  schema-valid proposed policy that removes or validly renews that acceptance changes that entry's
  review reason to `policy_change_review`, but never makes the acceptance effective in the current
  run. This relabelling permits a policy-only remediation PR to clear under
  `review-mode: codeowners` only when no other unaccepted gap or unwaived finding remains. If any
  expired acceptance remains in a policy-changing proposed policy, `coverage_acceptance_review` is
  recorded even when unmatched. An unmatched inactive authoritative acceptance on an unrelated PR
  emits the advisory `stale_acceptance_present` diagnostic. Missing, empty, wrongly typed, or
  malformed required authorization fields are a policy validation `ERROR` (`invalid_policy`), not a
  review-only condition (§8.4.3).
- An acceptance added or semantically modified in a PR is a PR-authored policy change: it cannot
  take effect in that PR (§8.3).
- Acceptances and their count are stated in the PASS text (§1.3).

## 7. Pipeline

### 7.1 Required initialization order

1. Validate CLI arguments, verify the deployment contract inputs available in Git (§8.6), and
   resolve the requested revisions to commit identities.
2. Verify required Git objects and determine the merge base; compute `target_drift`.
3. Build the authoritative `DiffModel` (merge-base..head) and detect whether `.verifyci/policy.toml`
   or any gate-integrity path (§8.5) is in the merge-base..head path set.
4. Load and validate the authoritative policy from `target_base_commit` (or enter the fail-closed
   onboarding bootstrap mode of §8.3 if `.verifyci/policy.toml` is absent at `target_base_commit`
   and added as a valid policy at `head_commit`); verify manifest and toolchain fingerprint.
   Validate the proposed head policy whenever the merge-base..head path set includes `.verifyci/policy.toml`.
5. Resolve changed scope, execute checks, aggregate results, and serialize evidence.

Policy loading cannot precede commit/object validation because the policy blob must be read
from an identified, verified commit. Target-base policy remains authoritative; the diff is
used only to determine whether the PR itself changed the policy or is bootstrapping a first policy.

### 7.2 Stages

```text
CLI
 |
 +- [0] argument and commit-identity validation
 +- [1] Git object verification + merge-base resolution + drift
 +- [2] DiffModel construction (merge-base..head) + gate-integrity path detection
 +- [3] target-base policy load + validation (or onboarding bootstrap) + proposed policy check + manifest check
 +- [4] scope resolution (cheap entity spans, hunk mapping)
 +- [5] demand-driven facts (VFIR, symbols, callers, summaries) -- sandboxed
 +- [6] checks: grounding, deletion, contract, security, semantic (shadow or blocking)
 +- [7] aggregation + waivers + coverage acceptances
 +- [8] canonical bundle + SARIF + exit code
```

After successful initialization, all manifest checks run. Grounding runs first and its result
is retained, but it is not a short-circuit. Absent a higher-precedence `ERROR`, a proven
security or semantic defect still establishes aggregate `FAIL` when grounding elsewhere is
inconclusive. `ERROR` retains highest precedence.

If an upstream failure prevents a check from executing, that check still receives a record:

- prerequisites remain trustworthy $\Rightarrow$ continue with other checks and preserve diagnostics;
- prerequisite is untrustworthy $\Rightarrow$ record `ERROR` with `not_executed` and the reason code.

If initialization fails before any check can execute, every manifest check receives `ERROR`
with `not_executed`, the initialization error is preserved, and the aggregate verdict is
`ERROR`. No PASS is emitted.

### 7.3 FactProvider boundary

`verifyci/index/provider.py` owns demand resolution:

- authoritative blob reads through `scm.git`;
- cache lookup, authentication, validation, sampled recomputation, and fallback;
- deterministic production of entity spans, file symbol facts, VFIR, summaries, and solver
  results, via sandboxed workers (§13.4);
- propagation of capability and coverage reasons.

`verifyci/index/symbol_index.py` owns symbol indexing and reverse lookups only. It does not
become an implicit owner of every fact source or of Git access.

Checks receive a `DiffContext` and a `FactProvider` interface. They never import `scm`,
`cli`, or storage modules.

## 8. Git truth, policy binding, and gate integrity

### 8.1 Git authority and hardened access

`verifyci/scm/git.py` is the only module authorized to access Git. It exposes a read-only,
commit-pinned object interface. The pipeline and `FactProvider` use it; checks do not.

The working tree is never authoritative. All base, merge-base, and head content is read from
Git objects. The gate requires a real repository; it does not trust files on disk.

**Plumbing only, hardened environment.** The adapter uses only plumbing commands
(`rev-parse`, `merge-base --all`, `cat-file --batch`, `ls-tree`, `diff-tree`, `rev-list`)
with these settings, all recorded in the toolchain fingerprint:

- `GIT_NO_REPLACE_OBJECTS=1` (replace refs and grafts are ignored);
- `GIT_NO_LAZY_FETCH=1` (a promisor/partial-clone miss is `missing_git_object`, never a fetch);
- `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` pointed at an empty file, `GIT_CONFIG_NOSYSTEM=1`,
  and `-c core.hooksPath=<empty>` `-c core.fsmonitor=false`;
- `-r --no-commit-id --no-ext-diff --no-textconv --no-color`, fixed rename detection
  (`--find-renames=60% --no-find-copies -l2000`), `-z` output. If the number of added/deleted
  file candidates in the diff exceeds the pinned rename limit (`2000`), the adapter does not
  silently degrade to unpaired adds/deletes: it records `rename_limit_exceeded` in scope
  diagnostics, affecting grounding/deletion coverage as `PARTIAL` (`mapping_unresolved`)
  whenever symbol or rename provenance is required;
- no use of `.gitattributes`, filters (smudge/clean), EOL conversion, or `.git/info` overrides:
  blob bytes are exactly the stored object bytes.

**Object-kind handling.**

| Kind | Handling |
|---|---|
| Regular file, executable | Read blob bytes; mode is part of provenance. |
| Symlink (`120000`) | The link target string is the content. It is never dereferenced, and no file outside the repository is read. Path rules apply; changes are path/target provenance only. |
| Gitlink / submodule (`160000`) | Path and commit ID only; no recursion. Reported as a `submodule` change; path `deny_changes` rules apply; submodule content is an `excluded_scope` entry. |
| LFS pointer | Detected by pointer format; treated as a binary blob by pointer identity. Real content is unavailable: recorded as `lfs_content_unavailable` and an `excluded_scope` entry; secret scanning cannot see it. |
| SHA-256 repositories | Supported; `inputs.object_format` is recorded and object IDs are algorithm-tagged. |

Shallow history that cannot establish a unique merge base yields `ERROR` (`shallow_history`).

### 8.2 Commit identities, merge base, and target drift

- CLI accepts the target base revision and head revision. The gate resolves `--base` to
  `target_base_commit` **at run time** and records the supplied name as `inputs.target_ref`.
  The Action bootstrap (§1.4) must resolve the target tip by fetching it immediately before invoking the core, not by reusing the event payload's stale base SHA; the core never fetches.
- The gate computes the merge base internally and verifies it is a common ancestor.
- The PR change set is `merge_base_commit..head_commit`.
- The policy is read from `target_base_commit`.
- The diff is never computed against the target tip unless the target tip is also the merge
  base.

If multiple merge bases exist, the gate returns `ERROR` (`ambiguous_merge_base`) unless an
explicit merge-base revision is supplied and verified as a common ancestor of both sides.

**Target drift.** $\text{target\_drift} = (\text{merge\_base\_commit} \neq \text{target\_base\_commit})$. Checks read
callers, callees, and references from the head, which still contains the *old* target. If the
target has since removed or changed something the PR depends on, the PR can pass here and break
on merge. v3.1 handles this explicitly:

- `target_drift` is recorded in the payload, and `target_changes_since_merge_base` is added to
  `excluded_scope[]` whenever it is true;
- policy `[gate] target_drift = "record"` (default) keeps the verdict unaffected;
- policy `[gate] target_drift = "require_zero"` yields `INCONCLUSIVE` with the run-condition code
  `target_drift` (Appendix A.6) when drift exists, forcing re-verification after rebase or on a merge candidate;
- **merge-candidate verification** (recommended for merge queues and merge-ref workflows):
  pass the queue's candidate commit as `--head` and the target tip as `--base`. The candidate
  descends from the target tip, so the merge base equals the target tip, drift is zero, and the
  PR's interaction with the current target is verified. No other change to the gate is needed.

The GitHub Action must fetch the target base, head, and enough history to establish the merge
base. A shallow checkout that cannot do so yields `ERROR`; it does not fall back to the target
tip or the working tree.

### 8.3 Policy cases

| Condition | Result |
|---|---|
| Invalid authoritative policy at target base | `ERROR` (`invalid_policy`) |
| Target base has no `.verifyci/policy.toml`, and PR adds a valid `.verifyci/policy.toml` | Onboarding bootstrap: run executes against the built-in minimal fail-closed policy (no exclusions, waivers, or acceptances) and yields `REVIEW` (`policy_change_review` and `gate_integrity_review`) if checks otherwise pass |
| Target base has no `.verifyci/policy.toml`, and PR does not add one | `ERROR` (`invalid_policy`) |
| PR-authored policy change: `.verifyci/policy.toml` appears in merge-base..head | `REVIEW` (`policy_change_review` and `gate_integrity_review`); head policy validated but not used to govern the PR |
| Head policy differs from target base only because the target branch advanced | No policy-change `REVIEW`; target-base policy remains authoritative |
| Invalid proposed policy schema when the PR changes it | `ERROR` (`invalid_policy` in `verdict.fault_reason_codes[]`); retain `policy_change_review` and `gate_integrity_review` in `verdict.reason_codes[]` |
| Proposed deletion: PR removes the policy file | `REVIEW` (`policy_change_review` and `gate_integrity_review`) when the authoritative policy is valid |
| Inactive waiver/acceptance in authoritative policy (expired or not-yet-effective) matches a current finding/gap and is not removed/renewed in the schema-valid proposal | `REVIEW` (`waiver_review` or `coverage_acceptance_review`) alongside the unwaived finding or unaccepted gap |
| Policy-changing PR removes or validly renews stale authoritative entries and proposed policy contains no expired waiver/acceptance | `REVIEW` (`policy_change_review`) when no other unwaived finding or unaccepted gap remains |
| Unmatched inactive waiver/acceptance in authoritative policy on an unrelated PR | Advisory diagnostic (`stale_waiver_present` or `stale_acceptance_present`); does not block |
| Any expired waiver/acceptance remains in the proposed head policy on a policy-changing PR, even if unmatched | `REVIEW` (`waiver_review` or `coverage_acceptance_review`); not eligible for `review-mode: codeowners` clearing |
| Valid active waiver from authoritative policy | Finding disposition `WAIVED`; all other gate requirements still apply |
| Valid active coverage acceptance from authoritative policy | Matching gaps accepted per §6.6 |
| New waiver or acceptance added in the PR | Cannot take effect in that PR; the policy path yields `REVIEW` (`policy_change_review` and `gate_integrity_review`) |
| Head policy used to govern the same PR | Forbidden |

Policy-change detection uses the merge-base..head change set, not a direct comparison between
head and target base. The path set is unfiltered by policy path classes; a PR cannot hide a
policy change by excluding its own path.

**Independent path-reason recording.** Stage 2 (§7.1) determines whether `.verifyci/policy.toml`
is in the merge-base..head path set before policy contents are validated. Whenever that path is
changed, record both `policy_change_review` and `gate_integrity_review` independently of the later
policy parse/schema result. These A.2 reasons remain in `verdict.reason_codes[]` even when a higher-
precedence `ERROR` wins; the associated integrity/policy fault is placed in
`verdict.fault_reason_codes[]` (for example `invalid_policy`). A later validation failure never
removes either detected review reason.

Detection sequence:

1. Check whether `.verifyci/policy.toml` exists at `target_base_commit`.
   - If present, read and validate it as the authoritative policy.
   - If absent, check whether `.verifyci/policy.toml` is added in merge-base..head: if added and schema-valid at `head_commit`, use the built-in minimal fail-closed bootstrap policy as authoritative (`policy.authoritative_blob_hash = null`, `policy.authoritative_policy_source = builtin_bootstrap_v1`, `policy.effective_policy_hash = <pinned built-in policy digest>`, `policy.pr_changed = true`, `policy.proposed_blob_hash = <head hash>`) and record both `policy_change_review` and `gate_integrity_review`; otherwise return `ERROR` (`invalid_policy`). If the path was changed, its two review reasons are still recorded as described above even when validation fails. The proposed head policy remains non-authoritative for this run.
2. The `DiffModel` path set and gate-integrity detection are already computed by Stage 2; they cannot be overridden by policy contents.
3. If `.verifyci/policy.toml` is not changed, do not validate the head policy and do not emit `policy_change_review` for that path. Changes to other §8.5 paths still record `gate_integrity_review`.
4. If `.verifyci/policy.toml` is changed, read the head blob:
   - missing $\Rightarrow$ proposed deletion $\Rightarrow$ record both review reasons and `REVIEW` (`policy_change_review` plus `gate_integrity_review`);
   - malformed or schema-invalid $\Rightarrow$ `ERROR` (`invalid_policy`), while retaining both review reasons in `verdict.reason_codes[]` and `invalid_policy` in `verdict.fault_reason_codes[]`;
   - schema-valid $\Rightarrow$ record both review reasons, record the proposed policy hash, and never use the proposal to waive findings or accept gaps in this run. Validate the record schema for all entries, but enforce `created <= as_of_date` only for waiver/acceptance records newly added or semantically modified relative to the authoritative policy using the exact namespace-plus-table-key identity and full normalized-record comparison in §§5.1 and 8.4.3. A renamed ID is remove-plus-add. Canonically unchanged future-dated authoritative entries remain valid but inactive. If any expired waiver or acceptance remains in the proposed policy, also record the corresponding `waiver_review` or `coverage_acceptance_review`, even if unmatched. Only a proposed policy with no expired entries can enter S1; then `policy_change_review` supersedes stale-entry review reasons for authoritative entries removed or validly renewed by the proposal.
5. Waivers and acceptances are part of the policy blob; one added or changed in the PR cannot
   neutralize that PR's findings or gaps. Those in the authoritative policy remain effective
   only when active under `created <= as_of_date <= expires`.

The evidence records `policy.pr_changed` and the proposed hash when one exists.

#### 8.3.1 Policy-remediation boundary (normative)

A proposed policy never takes effect in the run that proposes it (§8.3). Consequently adding,
renewing, or removing a waiver or acceptance in a PR can change only *which REVIEW reason* is
reported. It cannot change whether a finding is open or a gap is accepted. The scenarios:

| # | PR content | Findings and gaps in this run | Verdict | Exit | `review-mode: codeowners` |
|---|---|---|---|---:|---|
| S1 | Changes `.verifyci/policy.toml` with a schema-valid proposed policy that removes or validly renews every stale authoritative entry and leaves no expired waiver/acceptance in the proposed policy | No unwaived blocking finding; no unaccepted gap on a blocking check | `REVIEW` (`policy_change_review` and `gate_integrity_review`, because `.verifyci/policy.toml` is itself under the protected `.verifyci/` subtree; other changed §8.5 paths are recorded too) | 4 | Success iff the §8.7 conditions hold |
| S2 | Changes the policy but any expired waiver or acceptance remains in the proposed head policy, matched or unmatched | No separate unwaived finding/gap | `REVIEW` (`waiver_review` or `coverage_acceptance_review`, plus `policy_change_review` and `gate_integrity_review`) | 4 | Failure (not in the clearing set) |
| S3 | Policy change **and** code that still produces an unwaived blocking finding that a new or renewed waiver would cover | Finding stays `OPEN` | `FAIL` | 1 | Failure |
| S4 | Policy change **and** code that still leaves a coverage gap that a new or renewed acceptance would cover | Gap stays unaccepted | `INCONCLUSIVE` | 2 | Failure |

Rules:

1. Supersession of `waiver_review` / `coverage_acceptance_review` by `policy_change_review`
   applies per entry and only to the REVIEW label. It never changes a finding's disposition or
   a gap's status.
2. In S3 and S4, `policy_change_review` is still recorded in `verdict.reason_codes[]`, but the
   exit code is that of the winning verdict (§5.1). A combined PR therefore cannot become
   successful by renewing a waiver or acceptance.
3. A policy-only PR normally contains no changed scope that matches a stale authoritative entry.
   The entry is therefore an advisory maintenance diagnostic on an unrelated PR, but once the PR
   changes the policy, the proposed head policy is also checked: removing/renewing all expired
   entries permits S1; leaving any expired entry, matched or unmatched, triggers S2.
4. The supported route for S3 and S4 is the clearing workflow (§8.7): land the policy change on
   the target branch first, then re-run the code PR against the new authoritative policy.
5. S1–S4 are separate regression tests (§15.5, §15.8).

### 8.4 Policy format and safety

Policy is TOML at `.verifyci/policy.toml`, schema-validated. It contains:

- `[gate]` options (`target_drift`, deadlines);
- path classes: generated, vendored, tests, binary rules, and Python `source_roots`;
- entrypoints and public API symbols;
- `deny_changes` constraints over protected paths and exact symbols;
- `protected_guards`, `protected_errors`, `taint` sources/sinks/sanitizers, `forbidden_calls`;
- behavioral models: `decorators.transparent` and `calls.models`;
- secret allowlists by path and placeholder form;
- waivers and coverage acceptances;
- review requirements for policy changes.

Policy uses globs and exact qualified names only. It does not support user-supplied regular
expressions, code, templates, or includes. This avoids ReDoS and code-execution hazards. All
paths are normalized and confined to the repository; path traversal is an `ERROR`
(`path_traversal`).

#### 8.4.1 Qualified-name scheme (normative)

Every symbol string in policy and evidence is `module:qualname`.

| Language | `module` | `qualname` |
|---|---|---|
| Python | File path with the longest matching `source_roots` prefix removed, `.py` removed, trailing `__init__` removed, `/` $\rightarrow$ `.` | Python `__qualname__` form: `func`, `Class.method`, `outer.<locals>.inner` |
| TS/JS | Repository-relative path without extension, `/`-separated (`src/api/user`); `index` files are named by directory | Declared name, `default` for a default export, `Class.method`, `Class.#private` is out of scope |
| External callee | Import-resolved module path (`subprocess`, `flask`, `builtins`) | Attribute path (`run`, `request.args`) |

Examples: `app.auth:require_user`, `src/api/user:handler`, `subprocess:run`, `builtins:eval`.
Where a name is not statically resolvable the use is a coverage gap, never a match.

Globs: `*` matches within one segment (it does not cross `:` or `.`/`/` boundaries);
`**` crosses segments. Globs are permitted only in fields documented as accepting them
(public API, sinks, sources, forbidden calls, effects). `deny_changes.symbols` and waiver
symbols are exact.

#### 8.4.2 Schema semantics

`deny_changes` is the only general change-prohibition mechanism. Each entry has a table key
used as its `id`, optional `paths` globs, optional `symbols` exact qualified names, and a
`reason`. At least one of `paths` or `symbols` is required. Path rules match any changed
path whose base or head path matches; symbol rules match only an exactly mapped changed
entity. There is no regex, code, or allow-override inside a rule. `deny_changes` rules apply
regardless of path-class exclusions. Rules are evaluated in canonical table-key order. A
change matching multiple rules yields one finding with the first matching rule ID as primary
and all matched rule IDs recorded in evidence.

Semantic and security declarations:

```text
[protected_guards.<id>]        effects = [globs of effect callees]   # required
                               guard_calls = [exact guard callables]  # optional; semantics in §8.4.2.1(b)
                               paths = [globs]                        # required
                               reason
[protected_errors.<id>]        raises = [exact exception qualified names]
                               paths = [globs]  reason
[taint]                        sources = [globs]
[taint.sinks.<id>]             symbols = [globs]  kind = "sql|log|network|file|exec|serialize|html"
[taint.sanitizers.<id>]        symbols = [exact]  sinks = [sink ids]
[forbidden_calls.<id>]         symbols = [globs]  reason
```

Guard-related defects are defined in §8.4.2.1. `SEM-EXCEPTION-REMOVED` requires a
`protected_errors` entry. A declared sanitizer removes taint only for the sink ids it lists.

#### 8.4.2.1 Guard semantics (normative)

This subsection is the normative definition of `SEM-GUARD-REMOVED`, `SEM-GUARD-WEAKENED`, and
`SEM-GUARD-INVERTED` (§11.5). It refines the earlier guard-dominance prose; it adds no defect
ID. All definitions range over the VFIR of one function in two revisions, base (merge base)
and head.

**(a) Edges.** Every branch condition lowers to a `true` edge and a `false` edge. Every call
whose callee matches a `guard_calls` entry of the governing declaration lowers to a
`guard_pass` edge (the call returns normally) and a `guard_abort` edge (the call raises or
exits). An explicit `raise`/`throw` is an ordinary edge, and an exception handler is reachable
from the `guard_abort` edges of guard calls in its `try` body. Implicit exceptions from calls
that are not listed in `guard_calls` are **not** modelled (§10.3).

**(b) Declared meaning of `guard_calls`.** A listed callable `g` is a *raising guard* when its
result is discarded: `guard_pass` means authorized. When `g(args)` occurs inside a branch
condition, or its result flows into one, `g` is a *predicate guard*: a truthy return means
authorized (the `guard_abort` edge still exists for raising). The use is decided by call
position alone. By listing `g`, the policy author declares that "returns normally" (raising
guard) or "returns truthy" (predicate guard) means authorized; VerifyCI infers nothing about
any callable that is not listed.

**(c) Shared symbolic vocabulary (alignment).** Both revisions are encoded over one vocabulary
so that a satisfying assignment is meaningful in both:

1. *Parameters* are aligned by name and kind (positional-only parameters by position). An
   added, removed, renamed, or reordered parameter that cannot be matched makes the function
   `unalignable`.
2. *State reads* (attributes of parameters, globals, closure variables) are keyed by canonical
   access path, for example `request.user.role`. The at-entry value of an access path is one
   variable shared by both revisions. A read that follows a write to that path, or to a possible
   alias, in either revision is local to its revision; if such a value reaches a path
   condition it is `unalignable` unless the same assignment exists in both revisions.
3. *Call results.* A guard call `g` yields the Boolean atom `Pass_g(t1..tn)` over the aligned
   argument terms `ti`, shared across revisions. A callee declared `pure` under `calls.models`
   yields an uninterpreted function application `U_f(t1..tn)`, shared across revisions. Any
   other call whose result reaches a path condition is a gap (`unknown_call_on_path`).
4. *Effect instances.* An instance of a protected effect (callee matching `effects`, file
   matching `paths`) in base is paired with the head instance that has the same qualified
   callee and the same canonical aligned argument terms; ties are broken by dominance order. A
   pairing that stays ambiguous is `unalignable`.
5. *Branch/guard sites.* Branch-condition sites are paired by source/CFG correspondence and
   canonical aligned operand terms, not by exact predicate text alone; changing a comparison
   operator or Boolean connective at a paired site therefore remains classifiable as a
   predicate change. If multiple pairings remain possible, alignment is `unalignable`. Each
   path edge records the paired site identity, its polarity relative to the normalized predicate
   (with negation pushed through Boolean operators), and the actual revision-specific predicate.
   Equivalent normalized branch atoms share formula identity while retaining source-site
   provenance. Unrelated branch atoms are not deemed protecting literals merely because they
   occur in some path formula.

An `unalignable` outcome yields the coverage gap `semantic_alignment_unresolved` (Appendix
A.3, not acceptable) for the entity. It never yields a finding.

**(d) Path conditions.** For an effect instance `E`, `Φ_E` is the disjunction, over all CFG
paths from function entry to `E` (loops unrolled to the pinned deterministic bound; exceeding
it is `budget_exhausted`), of the conjunction of the edge conditions on that path: a branch
edge contributes its condition or the negation; `guard_pass` contributes `Pass_g(args)`;
`guard_abort` contributes `¬Pass_g(args)`. A path through a `guard_abort` edge exists only when
a handler in the function continues to `E`, so a `try/except: pass` around a guard call yields
a path that carries `¬Pass_g(args)`.

**(e) Detection predicate.** For each paired effect instance, `Δ(E) := Φ_E^head ∧ ¬Φ_E^base`
over the shared vocabulary. A guard defect is established only when `Δ(E)` is satisfiable,
the model replays in the VFIR evaluator for both revisions (`E` reached in head and not in
base), and frontend fidelity covers the constructs used (§6.5). `UNSAT` means no defect for
that instance; solver `UNKNOWN` is `solver_unknown`. A base effect instance with no head
counterpart (the effect was removed) and a head instance with no base counterpart (a new
effect) are out of scope for these IDs; the latter is the planned v3.2 item in §16.

**(f) Classification.** Let `L_base(E)` be the set of normalized Boolean literals `ℓ` over
aligned branch/guard atoms for which `Φ_E^base ⊨ ℓ`; equivalently, every satisfiable base path
conjunction to `E` entails `ℓ`. An atom is a normalized semantic condition, not an arbitrary
source line. The alignment table in (c) records the source sites that implement each atom and
pairs those sites across revisions. Therefore an ordinary branch atom that occurs with both
polarities on alternative base paths is not in `L_base(E)`, while the same required condition
expressed at multiple aligned sites can remain represented. Actual path formulas use the
revision-specific predicate at each paired site; changing `>` to `>=` does not by itself make
the paired site disappear.

When `Δ(E)` is satisfiable, classify in this order:

1. `SEM-GUARD-INVERTED`: for some `ℓ ∈ L_base(E)`, every satisfiable head path to `E` traverses
   the corresponding aligned guard site(s) only with the opposite normalized polarity, and no
   satisfiable head path traverses a corresponding site with the original polarity. Polarity is
   measured against the normalized predicate, not merely the raw true/false successor edge.
   A different comparison operator or connective at the same site is not alone an inversion.
2. `SEM-GUARD-REMOVED`: at least one head path that witnesses `Δ(E)` reaches `E` without
   effective protection by a required aligned guard. This includes (i) a required site absent
   from that path, (ii) continuation through a raising guard's `guard_abort` edge via an exception
   handler, or (iii) traversing the paired branch/guard site with the opposite normalized polarity
   when Rule 1 does not apply because another satisfiable head path still uses the original
   polarity. Case (iii) is a mixed-polarity bypass: the gate no longer prevents the effect for all
   inputs on that path, but it is not a global inversion because an original-polarity path remains.
   A paired site whose predicate text or Boolean relation changed is still a present site for this
   rule; it is not treated as absent merely because the changed predicate no longer entails the
   base literal. A distinct satisfiable head path that retains original polarity never cancels an
   absent-site, abort, or opposite-polarity bypass witness.
3. `SEM-GUARD-WEAKENED`: otherwise, when the relevant head path retains the paired guard site
   with the original normalized polarity but the actual predicate or Boolean relation/connective
   changed so that `Δ(E)` is satisfiable (for example `>` to `>=`, or `and` to `or`). A same-site
   predicate change is classified as weakened, not removed, unless Rule 1 establishes inversion
   or Rule 2 establishes an absent-site, abort-bypass, or mixed-polarity bypass path. This precedence is normative.

The classification is deterministic. Every class requires the same `Δ` witness and replay, and
its tests include exception-swallowing where both normal and handler paths reach the effect,
a boundary relaxation (`>` to `>=`) that must classify as weakened rather than removed, a guard
site absent on one satisfiable bypass path, a mixed-polarity bypass with both original- and
opposite-polarity head paths that must classify as removed, a globally inverted guard with no
original-polarity head path, repeated equivalent guards at separate sites, and an unrelated branch
that merges before the effect. An ambiguous site pairing yields
`semantic_alignment_unresolved`, not a finding.

**(g) Evidence and versioning.** Evidence records `Φ_E^base` and `Φ_E^head` (formulas and
canonical digests), the parameter, state-read and effect-pair alignment tables, the guard-call
declaration ID, and the solver and replay results. The definitions in this subsection are
`defect_semantics_version = 1` for the three IDs. No release has shipped a different
definition, so earlier document revisions are folded into version 1; any later change of
meaning increments the version, which invalidates waivers by design (§8.4.3).

**(h) Required validation before blocking.** For each of the three IDs the semantic corpus
(§11.5) must contain positives and negatives for: raising-guard and predicate-guard calls;
`try/except: pass` swallowing; polarity inversion; boundary relaxation; a guard that moved but
still guards; alignment failures (renamed parameter, changed state-read path, ambiguous effect
pairing) that yield `semantic_alignment_unresolved` rather than a finding; and replay for every
positive. The check stays at `shadow` until it meets §15.4 and §15.10 on that corpus.

Behavioral models (reviewable; they can hide defects, so they are policy changes):

```text
[decorators.transparent]       symbols = [exact decorator names]
    # does not change argument binding, control flow, or return value; treated as undecorated
[calls.models.<id>]            symbols = [globs]  model = "pure"
    # no observable effects, no raising beyond argument misuse; taint flows from arguments
    # to the return value
```

Suppression and modelling mechanisms are exactly: path-class exclusions, waivers,
coverage acceptances, secret allowlists, declared sanitizers, transparent decorators, and
pure-call models. Each is scoped and each is a reviewable policy change. Policy may extend the
versioned built-in patterns for secrets, dangerous calls, taint sources, and sinks; it cannot
disable a blocking check or globally suppress a defect family.

#### 8.4.2.2 Non-guard semantic predicates (normative)

This subsection defines the remaining semantic defect predicates `SEM-EXCEPTION-REMOVED` and
`SEM-BINDING-SWAP`. Both require aligned VFIR sites, a shared symbolic vocabulary, a satisfiable
witness, independent VFIR replay, and frontend-fidelity coverage (§6.5). A failure to align a
required entity, site, parameter, state read, callee, or caller is the coverage gap
`semantic_alignment_unresolved`, never a finding. A solver `UNKNOWN` remains unresolved.

**(a) `SEM-EXCEPTION-REMOVED`.** For a policy-protected exception class `R` declared by a
`protected_errors` entry, define `Φ_raise(R)^rev` as the disjunction of path conditions under
which execution of revision `rev` exits the protected function by propagating an uncaught
`R` (including subclasses only where the pinned frontend's exception relation proves that
membership). The trigger and its relevant input/state reads must align across base and head.
For aligned trigger inputs, define:

`Δ_err(R) := Φ_raise(R)^base ∧ ¬Φ_raise(R)^head`.

A candidate exists only when `Δ_err(R)` is satisfiable, the trigger is reachable, and replay on
the same shared input/state assignment confirms that base propagates `R` while head does not
propagate `R`. The finding is `SEM-EXCEPTION-REMOVED` only if the corresponding
`protected_errors` policy applies to the aligned function/path and the exception behavior is
within the declared frontend subset. A new unrelated exception, a changed exception type whose
subtyping is unknown, or an unaligned trigger is not this finding; it yields unresolved coverage
where relevant. The witness records the triggering path conditions, the uncaught exception
classification in both revisions, and replay results. This defect ID has
`defect_semantics_version = 1` for the initial release.

**(b) `SEM-BINDING-SWAP`.** Candidate detection pairs a base/head direct call site, or a tuple
return site and its unchanged aligned consumer, with the same resolved callee and unchanged
callee/caller contract. Let `B_base` and `B_head` map compatible argument/return positions to
aligned symbolic values. A swap candidate requires a non-identity permutation `π` over at least
two compatible positions, with `B_head(i) = B_base(π(i))` for the permuted positions, and no
corresponding compensating change to the callee contract or caller bindings. Define the shared
reachability/divergence predicate:

`Δ_bind := Φ_site ∧ (∨_{i: π(i) ≠ i} B_base(i) ≠ B_base(π(i)))`.

`SEM-BINDING-SWAP` is established only if `Δ_bind` is satisfiable and replay of both revisions
under the same assignment confirms that the aligned call parameter or consumer receives a
different value due to the permutation, with a witnessed observable divergence in the declared
VFIR semantics. A syntactic reordering alone is insufficient. If values are equal on the witness,
callee/caller contracts changed, or the caller is correspondingly adapted so that the end-to-end
binding is preserved, no finding is emitted for that candidate. Ambiguous site/value alignment
is `semantic_alignment_unresolved`. This defect ID has `defect_semantics_version = 1` for the
initial release.

**(c) Required corpus cases.** The semantic corpus (§11.5) must include positive and negative
cases for uncaught protected exceptions removed under aligned triggers, exception-type and
trigger misalignment, argument swaps with distinct versus equal values, tuple-return swaps,
callee and caller compensation, and an otherwise identical call with a changed contract. Every
positive must include a satisfiable solver assignment and independent VFIR replay. The semantic
check remains `shadow` until it meets §15.4 and §15.10.

#### 8.4.3 Waivers, acceptances, and fingerprints

A waiver is eligible for use in v3.x only when present in the authoritative target-base policy
and it carries non-empty `approved_by` and `reason`, plus ISO-date `created` and `expires` fields.
Missing, empty, wrongly typed, or malformed required fields, or `expires < created`, are schema
errors (`invalid_policy`, `ERROR`) in both authoritative and proposed policies; they are not
review-only conditions.

**Stable policy ID and normalized-record equality (normative).** The stable policy ID is the parsed TOML leaf-key string within its record namespace: the key in
`[waivers.<id>]` for a waiver or `[coverage_acceptances.<id>]` for an acceptance. The key's decoded
TOML value, not its raw header spelling or quoting, defines the ID; source spellings that parse to
the same key therefore identify the same record. IDs are compared only within the same namespace.
This policy-record ID is distinct from the waiver finding fingerprint, which determines which
finding a waiver matches. To decide whether a proposed record is unchanged, parse and schema-validate
both records, apply the same pinned schema normalization and default expansion used by the policy
canonicalization/hash path, and compare the complete normalized record objects. Compare every
schema-defined field and effective value, including `created`, `expires`, `approved_by`, `reason`,
fingerprint/matching fields, check or reason-code fields, scopes, and all other supported fields;
exclude only the enclosing TOML table key. Do not use the waiver finding fingerprint as a proxy for
record equality. Fields that are omitted but receive a schema-defined default compare by their
effective normalized value; a missing required field is an error, not a default. The comparison is
performed on the normalized objects before RFC 8785 JCS byte encoding and is not a raw text diff.
Renaming a waiver or acceptance table key is treated as removing the old record and adding a new
record; the new record has no same-ID authoritative counterpart.

The proposed-policy `created <= as_of_date` constraint applies only to a waiver newly added or whose
complete normalized record differs from the authoritative record with the same stable policy ID
(§5.1). An unchanged authoritative waiver copied into a proposed policy may be future-dated; it
remains structurally valid but inactive until its creation date. During onboarding bootstrap, where
there is no authoritative policy, every proposed waiver is treated as new. VerifyCI does not
authenticate the human identity represented by `approved_by`; that remains the target branch's
review-process responsibility. A structurally valid but inactive waiver follows the review
behavior in §5.3 and §8.3.1. Waivers have no fixed maximum lifetime in v3.1.x, but they must be
explicitly dated and must not be effective before `created`. Coverage acceptances follow the same
proposed-entry date rule (§6.6); their 180-day bound is also schema-validated.

A waiver is matched by a fingerprint: SHA-256 over canonical
`{check_id, defect_id, defect_semantics_version, repository-relative path, stable symbol
identity when available, normalized evidence identity}`. Evidence identity is redacted where
applicable. Commit IDs, line numbers, and the tool or check version are excluded so a waiver
survives rebases and tool upgrades; `defect_semantics_version` (declared per defect ID in the
`CheckSpec`) changes only when the *meaning* of the defect changes, which deliberately
invalidates waivers for re-review. Without a stable symbol identity, the waiver matches the
normalized span and is expected to expire quickly.

#### 8.4.4 `as_of_date` and expiry

Waiver and acceptance expiry would otherwise make results depend on wall-clock time, which
is not a canonical input. v3.1 makes it one:

- `inputs.as_of_date` is a UTC `YYYY-MM-DD` date recorded in the payload.
- CLI: `--as-of <date>`; default is the UTC date at run start. The Action takes the date from
  the runner clock and does not expose an override except for replay runs.
- A waiver or acceptance is active iff $\text{created} \le \text{as\_of\_date} \le \text{expires}$. An entry before its `created` date is not-yet-effective; an entry after `expires` is expired. Neither is active or may suppress a finding/remove a gap.
- A reproduction run passes the recorded `as_of_date`.

### 8.5 Gate-integrity paths (built in, non-configurable)

A PR that edits the gate's own controls can otherwise silence it. The following paths are
**gate-controlling** and built into the gate; policy cannot remove, narrow, or exclude them:

```text
.verifyci/**
.github/workflows/**
.github/actions/**
CODEOWNERS   .github/CODEOWNERS   docs/CODEOWNERS
```

Normatively these paths decompose into **protected subtrees** `S1 = .verifyci/`,
`S2 = .github/workflows/`, `S3 = .github/actions/` (every path with that directory prefix,
including paths that do not exist yet) and **protected files** `F1 = CODEOWNERS`,
`F2 = .github/CODEOWNERS`, `F3 = docs/CODEOWNERS` (exact, case-sensitive, repository-root
relative). "Every canonical path in §8.5" means every path under S1–S3 and each of F1–F3.

Any add, modify, delete, or rename touching one (base or head path) in merge-base..head
yields `REVIEW` with reason `gate_integrity_review`, the changed paths recorded in
`inputs.gate_integrity.changed_paths`. A change to `.verifyci/policy.toml` yields both
`gate_integrity_review` and `policy_change_review`: the first records modification of a protected
gate-control path, while the second records the policy-governance decision. These reasons are
independent and neither suppresses the other. The review is not waivable. It is `REVIEW`, not `FAIL`: such changes are legitimate but
require a human with authority.

The gate cannot stop a PR that deletes its own workflow step, because in that run the gate
does not execute. That is why §8.6 is a normative deployment requirement.

### 8.6 Deployment contract (normative for adopters)

VerifyCI's guarantees hold only when it is deployed so the PR cannot remove it. Adopters must:

1. Run the gate as a **required status check** supplied by a **required workflow / ruleset**
   defined outside the PR's control (organization or separate repository), not solely by a
   workflow file inside the PR branch.
2. Pin the Action by **full 40-hex commit SHA**. The Action refuses to run (`manifest_mismatch`)
   if its embedded toolchain fingerprint differs from the release manifest it ships with.
3. Enable **required review from code owners**, with `CODEOWNERS` covering every path in §8.5
   with at least one owner who is not the PR author's default reviewer pool.
4. Resolve the target tip by fetching during the run (§8.2); never rely on a cached base SHA.
5. Keep the cache key (§14) available only to trusted workflows.

Each control is classified by what the gate or Action can actually verify:

| Control | Verified? | Mechanism | Assumption recorded when unverified |
|---|---|---|---|
| Required workflow / ruleset | No | Needs an administrative token | `required_workflow_not_verified` |
| Required status check and required code-owner review (branch protection) | No | Needs an administrative token | `branch_protection_not_verified` |
| Action pinned by full SHA | Yes (release builds) | Compares the Action's own ref to a 40-hex SHA; failure is `deployment_contract_violation` | — |
| Toolchain matches release manifest | Yes | Fingerprint comparison; failure is `manifest_mismatch` | — |
| Target-base `CODEOWNERS` covers the §8.5 paths | Yes | Reads target-base Git and applies the §8.6.1 rule; failure is `deployment_contract_violation` under `review-mode: codeowners` (§8.7), otherwise recorded | `codeowners_coverage_missing` |
| Code owners named in `CODEOWNERS` exist and hold write access | No | Needs an administrative token | `codeowners_owner_validity_not_verified` |
| Target tip fetched fresh | No (the core is offline) | Bootstrap fetch; time recorded in envelope | `target_freshness_not_verified` |
| Cache key isolation | No | Secret-store configuration | `cache_key_isolation_not_verified` |

**`CODEOWNERS` ownership coverage** is decided by the conservative rule of §8.6.1. A failure is
handled as the table above states: `deployment_contract_violation` under `review-mode:
codeowners` (§8.7), otherwise the assumption `codeowners_coverage_missing` is recorded.

Assumption strings are entries in `assumptions[]`, not reason codes, and appear in every
bundle for every control that is not verified in that run.

**Adoption and release prerequisite.** Controls 1–3 (required workflow, branch protection with
code-owner review, SHA pin) are security assumptions, not optional hardening. A deployment
that does not satisfy them is not a supported deployment, and the PASS guarantee is claimed
only for supported deployments. The release must publish the contract (README and adoption
guide) with the table above, and the unverified controls must remain visible in every
bundle.

#### 8.6.1 `CODEOWNERS` ownership-coverage rule (normative)

Goal: establish from target-base Git alone that **every** path under S1–S3, including paths a
PR adds later, and each of F1–F3 resolves to at least one owner under GitHub's evaluation,
without implementing arbitrary glob semantics. The rule is deliberately conservative: it may
reject a file GitHub would accept, never the reverse. The recommended form at the end of this
subsection always passes.

1. **Active file.** At `target_base_commit` the active file is the first that exists among
   `.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`; the other two are ignored for
   evaluation. If none exists, coverage is unproven. A file larger than 3 MiB (a pinned
   conservative cap) or not valid UTF-8 is unproven.
2. **Supported subset and canonical pattern validation.** Blank lines and lines whose first
   non-space character is `#` are ignored. Every other line is a rule `pattern owner…`, split on
   ASCII whitespace. As in GitHub's documented syntax, a token beginning with `#` starts an
   inline comment only after at least one valid owner token has appeared; `pattern # comment`
   has no owner and is therefore ownerless/unsupported. An *owner token* is `@user` (`@`
   followed by alphanumerics and hyphens), `@org/team` (`@`, name, `/`, team slug of
   alphanumerics, `.`, `_`, `-`), or an email address (`local@domain` with a dot in the domain
   and no further `@`). A line is **unsupported** if it begins with `[` or `^[` (section
   headers), if its pattern contains `!`, `[`, `]`, or any backslash escape, if it contains
   `//`, or if any slash-delimited path segment is exactly `.` or `..` after removing at most
   one optional leading slash and one optional trailing slash, or if any owner token is not
   valid. The special broad patterns `*`, `**`, and `/**` are checked before segment
   validation. An unsupported line is treated as an ownerless rule whose pattern overlaps every
   protected path; it can never qualify as provably disjoint. If the file contains any section
   header, coverage is unproven, because sections add per-section ownership requirements that
   this rule does not evaluate.
3. **Covering rule.** For a protected subtree with directory segments `d1/…/dn`
   (S1: `.verifyci`; S2: `.github`, `workflows`; S3: `.github`, `actions`), a rule is a
   *covering rule* iff it has at least one valid owner token and its pattern, compared
   case-sensitively, is one of: `*`, `**`, `/**`, or for some `k` with `1 ≤ k ≤ n`:
   `/d1/…/dk/` or `/d1/…/dk/**`. For a protected file `f`, a covering rule has one of the same
   forms for any proper ancestor directory of `f`, or the exact anchored pattern `/f`. Patterns
   without a leading slash, other globs, and extensionless directory forms are not recognised.
4. **Non-interference.** Let `R_c` be the **last** covering rule in file order; if there is none,
   coverage is unproven. Every rule after `R_c` must be either (a) a rule with at least one
   valid owner token, whatever its pattern, because it can only substitute another non-empty
   owner list; or (b) an ownerless or unsupported rule whose pattern is **provably disjoint**
   from the protected path: the pattern has a leading `/` and, after the canonical-segment
   validation in step 2, for some `i ≥ 1` its first `i` segments contain no `*` or `?`, its
   first `i−1` segments equal the protected path's first `i−1` segments, and its `i`-th segment
   differs from the protected path's `i`-th segment. Invalid/non-canonical patterns are never
   eligible for this proof. Any other ownerless or unsupported rule after `R_c` leaves coverage
   unproven.
5. **Result.** Coverage is proven iff steps 1–4 succeed for each of S1, S2, S3, F1, F2, and F3.
   Only pattern text and file order are used; no filesystem is probed. A path added later under
   S1–S3 matches `R_c`'s form by construction, and by step 4 no later rule can remove its
   ownership.
6. **Owners are not verified.** Whether an owner exists, is a visible team, or holds write access
   cannot be read from Git, and GitHub ignores owners without write access. The assumption
   `codeowners_owner_validity_not_verified` is recorded in every bundle.

Recommended form (passes by construction; place it after any broader rules):

```text
/.verifyci/              @org/verifyci-owners
/.github/workflows/      @org/verifyci-owners
/.github/actions/        @org/verifyci-owners
/.github/CODEOWNERS      @org/verifyci-owners
/CODEOWNERS              @org/verifyci-owners
/docs/CODEOWNERS         @org/verifyci-owners
```

The evaluator is validated on a corpus (§15.1, §15.6) that includes: the recommended form
(proven); an owned `*` rule followed by an ownerless `*.yml` (unproven); a trailing ownerless
`/.github/**` (unproven); a trailing ownerless `/docs/` (unproven for F3); a trailing ownerless
`/src/legacy/` (proven); section headers (unproven); negation and escape syntax after the
covering rule (unproven); non-canonical `//.verifyci/**`, `/./.verifyci/**`, and `/src/../.verifyci/**`
patterns (unproven and never treated as disjoint); the documented `/.verifyci/ @org/team # note`
inline-comment form (accepted); a `pattern #comment` line with no owner (unproven); an email owner
(accepted); a missing active file; `.github/CODEOWNERS` shadowing a root file; an oversized file;
and a workflow path added later under S2 (covered).

### 8.7 CLI contract and Action mapping

```text
vc gate --repo <dir> --base <target-base-rev> --head <head-rev>
        [--merge-base <rev>] [--format json|sarif] [--output <path>]
        [--as-of <YYYY-MM-DD>]
        [--cache-dir <dir> | --no-cache] [--allow-local-cache] [--jobs <n>]
```

- `--base` is the target-branch revision whose policy is authoritative; it is not the merge
  base. It is resolved at run time and recorded with `target_ref`.
- `--head` defaults to `HEAD`; CI passes the exact PR commit or merge-candidate commit.
- `--merge-base` is accepted only when verified as a common ancestor; otherwise `ERROR`.
- `--format json` emits the canonical evidence bundle; `sarif` emits CI output.
- `--jobs` affects only fact-computation parallelism and never semantics.
- The core has no patch-file input, network access, or repository execution, and it never fetches (§1.4).
- Exit codes: `0` PASS, `1` FAIL, `2` INCONCLUSIVE, `3` ERROR, `4` REVIEW.

**Action mapping.**

| Exit | Job result |
|---:|---|
| 0 | success |
| 1, 2, 3 | failure; summary states verdict, `blocking_findings_present`, and fault codes |
| 4 | failure by default (`review-mode: fail`) |

`review-mode: codeowners` maps exit 4 to success **only when** every REVIEW reason code is in
`{policy_change_review, gate_integrity_review}` and the target-base `CODEOWNERS` covers all §8.5 paths (§8.6.1); otherwise it fails. Those two reasons arise only from changes to paths that `CODEOWNERS`
review governs, so native code-owner approval is the clearing control. Other REVIEW reasons
(`waiver_review`, `coverage_acceptance_review`) fail unless the PR itself modifies `.verifyci/policy.toml`
with a schema-valid proposed policy that removes or renews the expired entry (which may replace
an expiry-review reason with `policy_change_review` only under the supersession boundary in
§5.3 and §8.3.1). Missing or empty authorization fields are `invalid_policy` errors and cannot
be cleared through this review-mode exception.

**Clearing workflow.**

1. The gate prints each finding's fingerprint (waivers) or each gap's reason code and subject
   (acceptances).
2. A policy PR to the *target branch* adds, renews, or removes the waiver or acceptance; `CODEOWNERS`
   review approves it, and it becomes authoritative once merged.
3. The original PR is rebased or re-run; the authoritative policy now applies.

## 9. Scope and grounding

### 9.1 Entity mapping

Entity spans are extracted cheaply in Stage 4, before full lowering. Stage 5 lowers VFIR only
for changed entities and affected callers.

| Change | Required mapping |
|---|---|
| Modified entity | Exactly one base entity and exactly one head entity |
| Added entity | No base entity and exactly one head entity |
| Removed entity | Exactly one base entity and no head entity |
| Supported module-level edit | Exactly one recognized module-level construct |
| `other_text` | Changed text in a file with no entity structure (docs, YAML, JSON, config, unsupported-language text): line and byte provenance only |
| Ambiguous or unsupported mapping in a supported-language file | Explicit unresolved scope with coverage/reason codes |

Ambiguity is not itself a defect. It produces unresolved scope, attributed to the check whose
scope needs the mapping, and `INCONCLUSIVE` unless another proven blocking defect establishes
`FAIL`.

### 9.2 Grounding check contract

| Field | Definition |
|---|---|
| Declared defect | `GRD-UNGROUNDED-EDIT`: a changed path or exactly mapped entity matches an active `deny_changes` rule. Path matches are established from the base/head path and changed span or blob identity; symbol matches require exact entity mapping. A mapping failure alone is not this defect. |
| Integrity errors | Deleted bytes disagree with the pinned base blob; commit/tree/blob/merge-base identity contradicts pinned inputs; internally generated diff is inconsistent. Recorded as `ERROR` diagnostics, not findings. |
| Unmapped changes | `other_text` hunks are **provenance-only and never make coverage partial**. A hunk in a supported-language file with no supported mapping is unresolved scope (`mapping_unresolved`) **only when it can matter**: an active symbol rule's module identity matches the file, or the rule's symbol cannot be resolved to a module. Otherwise it is classified `other_text`-equivalent for grounding (it remains visible to other checks under their own scope rules). A `deny_changes` path rule independently establishes a violation regardless. |
| Relevant scope | Every changed path in merge-base..head and every active `deny_changes` rule. Text hunks are mapped to entities or `other_text`; binary, symlink, gitlink, and LFS changes are path/provenance-only but are still evaluated by path rules. Policy-excluded files receive explicit not-applicable results with exclusion evidence unless a `deny_changes` path or symbol rule applies. |
| Applicability evidence | At least one changed file or hunk not excluded by authoritative policy, or at least one `deny_changes` rule applicable to the change set. No changes, or all changes excluded with no applicable deny rule, $\Rightarrow$ `NOT_APPLICABLE` with exclusion evidence. |
| Supported subset | Language-independent byte/line/path mapping and exact symbol matching. Path rules apply to every object kind; symbol rules require exact entity spans and apply only to supported-language text. Symbol rules over unsupported-language files are `UNKNOWN`, never `NOT_APPLICABLE`; path rules still apply. |
| Required evidence | Exact `deny_changes` rule IDs (primary and all matches), matched path or exact symbol, changed span or path/blob/mode identity, base/head blob IDs, and the effective `authoritative_policy_hash` plus `authoritative_policy_source` defined in §6.3 (including `builtin_bootstrap_v1` during onboarding). Integrity errors cite expected/actual object IDs in `diagnostics`. |
| Coverage | `COMPLETE` when every in-scope changed path is classified (modified/added/removed entity, supported module-level edit, `other_text`, binary, symlink, gitlink, LFS pointer, or path-only), excluded paths have exclusion evidence, every active `deny_changes` rule is evaluated, and all provenance checks agree. `PARTIAL` when a symbol rule cannot be resolved because mapping is ambiguous, or when `rename_limit_exceeded` prevents a symbol/rename mapping that an active rule or another required grounding operation actually needs. If the rename limit is exceeded but all required rules are path-only and remain decidable, record `rename_limit_exceeded` as a diagnostic and keep grounding coverage `COMPLETE`. Path rules are always resolvable from paths. Missing policy or objects are `ERROR`. |
| Failure conditions | Path or exact symbol match $\Rightarrow$ `FAIL`. Integrity mismatch $\Rightarrow$ `ERROR`. Ambiguous symbol rule alone $\Rightarrow$ `INCONCLUSIVE`. |
| Frozen corpus | Modified/added/removed entities, module-level edits, boundary hunks, duplicate lines, CRLF/LF, Unicode, renames, path-only/mode-only changes, generated/vendored paths, policy exclusions, protected-path modification/addition/deletion/rename, protected binary path, protected symlink/submodule, protected-symbol modification/deletion, ambiguous protected symbol, path-glob boundaries, no `deny_changes` rules, **README/YAML/doc-only edits with and without symbol rules**, tampered diff models, stale base, wrong merge-base, missing blobs. |

Fabricated-removal detection is an integrity error in commit mode. A future patch-input mode
would require a new `CheckSpec`; v3.x does not include it.

A `deny_changes` path rule can establish a violation without entity mapping: the prohibition
is on the path and the changed span is exact. A symbol rule cannot: a protected symbol that
cannot be mapped is unresolved scope and yields `INCONCLUSIVE`. A general rule requiring all
changes to map to an entity is not a `deny_changes` rule and cannot turn mapping failure into
`FAIL`.

## 10. Frontend and VFIR

### 10.1 Frontends

- Python: standard-library `ast`.
- TypeScript/JavaScript: tree-sitter with pinned grammar versions.

Both lower supported constructs into one Verified Function IR (VFIR). VFIR contains entities,
CFG, SSA values, guards, calls, returns, effects, exceptions, and capability annotations.

### 10.2 Capabilities

The canonical `Capability` enum used by `CheckSpec.required_capabilities` and contract
validation is the closed set:

```text
entity_spans  signature  cfg  ssa  calls  effects  exceptions  types  taint
symbols  references
```

Each capability has one normative provider class:

| Provider class | Capabilities | Contract |
|---|---|---|
| Frontend / VFIR lowering | `entity_spans`, `signature`, `cfg`, `ssa`, `calls`, `effects`, `exceptions`, `types`, `taint` | Declared per entity and tied to the pinned frontend/toolchain and fidelity evidence. |
| Symbol/reference index | `symbols`, `references` | Produced by the bounded symbol and reference index from authoritative Git blobs; not implied by `entity_status = LOWERED`. |

A check declares the capabilities it requires using this single enum, independent of provider.
The `CheckSpec` validator rejects unknown capability names and validates that each required
capability has a registered provider for the release. At run time, the `FactProvider` must
establish each required capability for every relevant entity or scope item. A capability that
is unavailable from its provider downgrades coverage and produces explicit reason codes; it
never silently skips analysis. For example, the deletion check in §11.3 requires both `symbols`
and `references` even when VFIR lowering is otherwise complete.

Every frontend entity also has exactly one `entity_status`:

| Status | Meaning |
|---|---|
| `LOWERED` | A valid VFIR representation exists for all constructs in the frontend's declared supported subset for this entity. |
| `PARTIAL` | VFIR exists, but at least one construct, edge, binding, or fact relevant to the entity is unresolved or conservatively approximated; corresponding missing capabilities and coverage reasons are recorded. |
| `OPAQUE` | A trustworthy VFIR for the entity cannot be produced, for example after a parse failure or a syntax-version mismatch. Grounding may still use raw blob/provenance facts. |

`entity_status` is distinct from `CheckResult.coverage`. For any check whose relevant scope
requires a capability not established for an entity, a `PARTIAL` or `OPAQUE` status forbids
`COMPLETE` coverage. Use `PARTIAL` when the affected entity and gap are known and bounded; use
`UNKNOWN` when the scope or candidate set cannot be reliably enumerated. A check that needs only
raw path/blob provenance is not downgraded solely because VFIR is unavailable, provided its own
scope and candidate discovery remain complete. `LOWERED` alone does not imply a check has all
the capabilities it requires; the declared capability set is checked independently.

### 10.3 Supported subset, fidelity, and grammar versioning

Every supported construct must have:

- a frontend conformance test (source $\rightarrow$ expected VFIR facts);
- a differential-fidelity test against CPython or Node for trusted, controlled fixtures.

Differential tests run only in VerifyCI's isolated CI. They never execute arbitrary
repository code during PR verification. They compare return values, exceptions, evaluation
order, and modeled effects for constructs within the declared subset.

A fidelity mismatch invalidates the affected capability and prevents semantic promotion.
Runtime evidence cites the frontend version, capability set, and fidelity corpus hash.

**Python grammar versioning.** `ast` is tied to the interpreter version in the pinned
toolchain. Source using syntax newer than the pinned interpreter fails to parse; this is
reported as `unsupported_syntax_version` (not a generic `parse_error`) so the gap is
diagnosable, and is an acceptable gap for non-semantic checks only by explicit acceptance.
Syntax older than the pinned interpreter parses normally.

A parse error in a changed file produces `OPAQUE` with `parse_error`; it never crashes the
gate. Grounding may still establish provenance. Semantic, contract, and taint coverage for the
affected entity becomes `PARTIAL` or `UNKNOWN`. Parse input exceeding the deterministic size or
depth budget yields `parse_resource_limit` and the same effect.

Known assumptions are explicit:

- unknown decorators are opaque wrapper effects (`unknown_decorator`); if they can change
  argument binding or control flow the function is `PARTIAL`, unless declared transparent in
  policy (§8.4.2);
- implicit exceptions from calls not listed in `guard_calls` are not modelled; the bundle
  records `implicit_exceptions_not_modeled` in `assumptions[]` whenever the semantic check
  ran (§8.4.2.1(a));
- async scheduling and external concurrency are outside intraprocedural semantics;
- closures are supported only where capture and mutation are in the declared subset;
- Python and JS evaluation order is modeled only for supported expressions;
- dynamic imports, `eval`, proxies, and computed dispatch are `PARTIAL` or `OPAQUE`
  (`dynamic_call`).

## 11. Checks

### 11.1 Common rules

- `PASS` requires `COMPLETE` coverage (after accepted gaps).
- `FAIL` may coexist with `PARTIAL` or `UNKNOWN` coverage.
- `NOT_APPLICABLE` requires positive applicability evidence.
- No blocking finding without validated evidence of its declared kind.
- Budget exhaustion without a witness $\Rightarrow$ `INCONCLUSIVE`; after a witness, the finding survives.
- Unsupported relevant language/capability $\Rightarrow$ `UNKNOWN`, never `NOT_APPLICABLE`.
- Internal inconsistency or an execution fault, other than deterministic budget exhaustion
  or a watchdog interruption, $\Rightarrow$ `ERROR`. An `ERROR` may carry validated findings; preserve
  them and apply aggregate precedence (§6.2).
- Each check has a frozen corpus, per-defect thresholds, and replayable witness tests.
- A check cannot enter the registry at a given maturity without a `CheckSpec` and passing the
  evidence requirements of that maturity (§15.4).

### 11.2 `grounding`

Defined in §9.2. It runs first, its result is retained, and it does not suppress other checks.

### 11.3 `deletion`

| Field | Definition |
|---|---|
| Declared defects | `DEL-REACHABLE-SYMBOL`: removed symbol remains reachable from an entrypoint, export, public API, or live reference. `DEL-DANGLING-REFERENCE`: head references a symbol with no definition. `DEL-DYNAMIC-REFERENCE`: a dynamic reference is proven to target a removed symbol. |
| Coverage limitation | An unresolved dynamic target is `dynamic_target_unresolved`, yielding `INCONCLUSIVE` when relevant. It is not a defect ID. |
| Relevant scope | Removed or renamed symbols at module, class, and export level; references from imports, `__all__`, barrel files, call sites, entrypoints, and tests. |
| Applicability evidence | At least one removed symbol in a non-excluded path. No removals $\Rightarrow$ `NOT_APPLICABLE`; all removals excluded $\Rightarrow$ `NOT_APPLICABLE` with path evidence. |
| Supported subset | Python and TS/JS symbol facts from bounded syntax-only parsing. Requires `symbols` and `references` capabilities. Other languages $\Rightarrow$ `UNKNOWN` when removal is relevant. |
| Required witness | Symbol identity, base definition span, and a live reference path; or a head reference with no definition; or a dynamic dispatch site proven to resolve to the removed symbol. |
| Coverage | `COMPLETE` when every removed symbol and its reference closure is resolved. `PARTIAL` when dynamic dispatch exists in importing modules, or when `rename_limit_exceeded` prevents a rename/symbol pairing needed to enumerate the removed-symbol reference closure. If no required deletion mapping is affected, retain the diagnostic without downgrading coverage. `UNKNOWN` for unsupported language scope. |
| Failure conditions | Proven live reference, dangling reference, or proven dynamic reference $\Rightarrow$ `FAIL`. Unresolved dynamic target alone $\Rightarrow$ `INCONCLUSIVE`. Index inconsistency $\Rightarrow$ `ERROR` (`index_inconsistency`). |
| Frozen corpus | Unused private symbol; used export; re-export through `__init__`/barrel; rename with all refs updated; rename with a missed ref; test-only reference; `__all__`; TS default export; deleted module; dynamic `getattr`; computed property; string dispatch; generated-path exclusion; multi-file package. |
| Test references | Count as live by default. |

### 11.4 `contract`

| Field | Definition |
|---|---|
| Declared defects | `CTR-SIGNATURE-BREAK`: parameter, return, async, or visibility change incompatible with a resolved caller or declared public API. `CTR-EXPORT-BREAK`: removed/renamed export still imported or declared public. `CTR-CALL-INCOMPATIBLE`: changed call site disagrees with an unchanged callee. |
| Relevant scope | Changed, added, or removed exported/called symbols; repo-internal call sites; policy-declared public API. External consumers are an explicit excluded assumption unless declared public. |
| Applicability evidence | At least one signature, export, or call-site change in scope. Otherwise `NOT_APPLICABLE` with inspected scope. |
| Supported subset | Python and TS/JS declared signatures, arity, parameter kinds, defaults, keyword names, return annotations, export/visibility, async/sync. Lightweight type compatibility only. Requires `signature`, `calls`, `types`. |
| Required witness | Base/head signature diff plus a call site whose argument binding fails; or a head import with no matching export; or a public-API policy declaration with the breaking change. |
| Coverage | `COMPLETE` when all relevant callers are resolved and type facts are sufficient. `PARTIAL` on dynamic calls, `*args`/`**kwargs`, unresolved imports, computed properties, or unknown types. `UNKNOWN` for unsupported language scope. |
| Failure conditions | Proven incompatibility $\Rightarrow$ `FAIL`. Unresolved relevant callers/types $\Rightarrow$ `INCONCLUSIVE`. Internal inconsistency $\Rightarrow$ `ERROR`. |
| Frozen corpus | Optional parameter addition; removed used parameter; positional reorder; keyword rename; default changes; positional-only parameters; overloads; TS union/structural types; `**kwargs`; dynamic import; public API break; async-to-sync change; caller-only break; external-only consumer. |
| Evidence bar | Every blocking finding cites a concrete call site or public-API policy. |

### 11.5 `semantic`

| Field | Definition |
|---|---|
| Declared defects | `SEM-GUARD-REMOVED`, `SEM-GUARD-WEAKENED`, `SEM-GUARD-INVERTED`: a paired protected effect becomes reachable in head for an input on which base did not reach it, that is, `Δ(E) = Φ_E^head ∧ ¬Φ_E^base` is satisfiable and replay-confirmed, labelled per §8.4.2.1(f) as a removed or exception-swallowed guard, a weakened boundary, or an inverted polarity. `SEM-EXCEPTION-REMOVED`: the policy-protected uncaught-exception behavior differs under an aligned trigger and satisfies `Δ_err(R)` in §8.4.2.2(a). `SEM-BINDING-SWAP`: an aligned call or tuple-return binding changes by a non-identity permutation and satisfies `Δ_bind` plus replay requirements in §8.4.2.2(b). Guard and exception defects require `protected_guards` / `protected_errors` declarations (§8.4.2); `SEM-BINDING-SWAP` requires none. |
| Relevant scope | Modified functions with body changes; direct callees needed to model calls; direct callers needed to judge return swaps. Added and removed entities are out of scope. |
| Applicability evidence | At least one modified entity whose normalized body digest changed. No body change, or comment/whitespace-only change $\Rightarrow$ `NOT_APPLICABLE` with digest evidence. |
| Supported subset | Python and TS/JS structured control flow, assignments, direct calls, returns, raises/throws, try/except, boolean/comparison expressions, simple containers. Requires `cfg`, `ssa`, `calls`, `exceptions`, `types`. Unknown decorators are assumptions; dynamic calls, proxies, `eval`, computed property calls, unresolved closures $\Rightarrow$ `PARTIAL`. |
| Method | Candidate detection from VFIR diff $\rightarrow$ bounded symbolic path formulas $\rightarrow$ deterministic Z3 `rlimit` $\rightarrow$ model $\rightarrow$ VFIR replay $\rightarrow$ finding only if replay confirms divergence. Solver `UNKNOWN` is not a defect. |
| Required witness | Concrete input/state, base path, head path, and observable divergence. Evidence includes solver result, replay result, frontend fidelity corpus hash, and `witness_level: ir`. |
| Coverage | `COMPLETE` when every modified entity has required capabilities, candidate discovery is complete for the declared patterns, and every candidate is proven or refuted. `PARTIAL` when any relevant entity is partial/opaque, any candidate is `UNKNOWN`, or alignment fails (`semantic_alignment_unresolved`). `UNKNOWN` for unsupported language scope. |
| Failure conditions | SAT + successful replay + fidelity coverage $\Rightarrow$ `FAIL`. UNSAT $\Rightarrow$ no defect for that candidate. `UNKNOWN`, unsupported construct, or budget exhaustion without witness $\Rightarrow$ `INCONCLUSIVE`. Replay mismatch or evaluator inconsistency $\Rightarrow$ `ERROR` (`witness_replay_mismatch`). |
| Frozen corpus | Protected guard removed with sink reachable; guard wrapped in `try/except: pass`; raising-guard versus predicate-guard call; renamed parameter and ambiguous effect pairing (alignment gap); guard and effect moved; guard strengthened; guard inverted; boundary weakened/strengthened; dead guard removal (UNSAT); argument swap with unchanged callee; swap with callee also swapped; return swap with caller adapted; return swap in public API; protected exception removed; equivalent refactor; decorator opacity and transparent decorator; dynamic call; nested guards; short-circuit; try/except; async; solver `UNKNOWN`; budget exhaustion. |

The semantic check does not claim general equivalence. It claims a declared regression
pattern was disproved, proven with a replayable IR-level witness, or left unresolved.
v3.1.0 ships it at `shadow` maturity (§16).

### 11.6 `security`

| Field | Definition |
|---|---|
| Declared defects | `SEC-SECRET`: offline-validated credential material introduced in changed text. `SEC-SECRET-TO-SINK`: validated secret flows to a log, network, serialization, or persistence sink. `SEC-TAINT-TO-SINK`: untrusted input reaches a policy-defined dangerous sink. `SEC-DANGEROUS-CALL`: exact policy-forbidden call introduced. |
| Sub-analyses | Secrets, taint, dangerous calls. Each has its own `CheckResult` record with independent outcome, coverage, findings, diagnostics, and applicability. |
| Secret "validation" | There is no network access, so "validated" means **offline** validation only: provider prefix/format, length and charset, embedded checksum (for example GitHub token CRC32), PEM/key structure, JWT structure, plus entropy and context. A candidate that passes format validation is a finding; a candidate that cannot be classified is `secret_candidate_ambiguous` and `INCONCLUSIVE`, never dropped. Live liveness is out of scope and must be stated in the finding message. |
| Relevant scope | Changed lines, enclosing entities, forward taint closure to sinks, and direct caller/callee summaries needed to connect sources and sinks. **Secret scanning applies to every changed text object, including files in policy-excluded (generated/vendored) path classes**; allowlists apply by authoritative path only. **Dangerous-call scanning** examines every added/modified head-side line in non-excluded files and every added/modified head-side line in generated or vendored path classes; generic path-class exclusion never suppresses this scan. Added files are scanned in full, not only at changed-line granularity. Deleted base-side text is considered for comparison but cannot by itself produce an `introduced` dangerous-call finding unless the corresponding head-side code contains the forbidden call. Taint is not applied inside excluded classes. |
| Applicability evidence | Secret scan: every changed text file. If at least one changed text file exists, a clean complete scan is `PASS`; if no changed text exists, the secret sub-analysis is `NOT_APPLICABLE` with evidence. Taint: may be `NOT_APPLICABLE` only when no relevant constructs exist and this is positively established. Dangerous calls: candidates from changed lines. |
| Supported subset | Python and TS/JS taint through assignments, arguments, returns, string/template construction, simple containers, and common stdlib sinks. Secret scanning is language-independent. Requires `taint`, `calls`, `types` for taint. Dynamic dispatch, reflection, `eval`, encoded blobs, or unknown calls on a relevant path $\Rightarrow$ `PARTIAL`. Calls declared `pure` or sanitizers in policy are modelled accordingly. Other languages $\Rightarrow$ `UNKNOWN` for taint; text secrets still scan. |
| Required witness | Exact source/sink spans; redacted secret with pattern/format-validation evidence; taint path with per-edge justification; policy rule ID. Dangerous call: exact span and resolved callee. |
| Coverage | `COMPLETE` when changed text is fully scanned and taint candidates are resolved. `PARTIAL` for unknown calls on relevant paths, dynamic dispatch, unresolved aliases, or unclassifiable encoded content. `UNKNOWN` for unsupported taint language scope. |
| Failure conditions | Validated secret, resolved taint path, or exact forbidden call $\Rightarrow$ `FAIL`. Ambiguous encoded secret or unresolved relevant taint path $\Rightarrow$ `INCONCLUSIVE`. Unknown call $\Rightarrow$ `INCONCLUSIVE` only when it can affect a relevant source-to-sink path. Internal scanner fault $\Rightarrow$ `ERROR`. |
| Candidate dropping | An ambiguous candidate cannot be dropped merely because it is hard to classify. Dropping requires positive evidence that it is outside the declared defect set or a supported benign case (`candidate_dropped_benign`, `candidate_outside_defect_set`). |
| Frozen corpus | Provider keys, private keys, JWTs, generic high entropy, base64/hex, placeholders, environment references, test fixtures, allowlisted paths, **secrets added in vendored/generated paths**; request $\rightarrow$ SQL/log/subprocess/file; parameterized query (PASS); declared sanitizer (PASS); cross-file taint; TS `innerHTML`/`child_process`; dynamic alias; unknown call; pure-modelled call; **new vendored directory with a forbidden call; forbidden call added to or modified on a changed head-side line in an existing vendored/generated file; deletion-only base lines do not create an introduced-call finding**; budget exhaustion. |
| Redaction | Redaction rate 1.0; allowlists are authoritative only from target-base policy. |

Security sub-result aggregation: each sub-analysis has its own outcome, coverage, findings,
and diagnostics. The top-level outcome is the highest-precedence sub-outcome using
`ERROR > FAIL > INCONCLUSIVE > PASS > NOT_APPLICABLE`. The top-level `findings[]` contains
every sub-analysis finding exactly once, keyed by the canonical finding identity used for
waiver fingerprints; the sub-results retain the same findings for attribution, so no finding
is discarded. The top-level `diagnostics[]`, `reason_codes[]`, and `evaluated_scope` include
the sub-analysis values and any aggregation-added entries. If one sub-analysis establishes a
defect and another encounters an internal error, the top-level outcome is `ERROR` and the
validated finding remains present in both the sub-result and the top-level findings. An
invalid sub-result (for example, `PASS` with `PARTIAL` coverage or `FAIL` without a finding)
is treated as `ERROR` (`invalid_check_result`). Top-level coverage is the weakest coverage
among applicable sub-analyses (`UNKNOWN` weaker than `PARTIAL`, `PARTIAL` weaker than
`COMPLETE`); if no sub-analysis is applicable, coverage is `COMPLETE` for the
not-applicable decision.

### 11.7 Shadow and advisory tier

The schema, registry, and orchestrator support checks that run and report without affecting
the verdict. `shadow` is such a tier for a **blocking-capable** check that has not yet earned
enforcement: it executes with its normal budgets, its findings appear as advisory annotations
(SARIF level `note`), its faults are tool notifications, and its results feed the field data
used to promote it. Heuristic advisories (concurrency, complexity, coverage) remain deferred.

### 11.8 Registry gate and maturity

A check is registered with a `CheckSpec`:

```text
id, version, maturity, spec_core_hash, promotion_record_hash (null at shadow), corpus_id, corpus_hash, heldout_corpus_hash, mined_corpus_id,
defect_ids[], defect_semantics_versions{},
precision_threshold, recall_lower_bound_threshold,
per_defect_thresholds, min_cases_per_defect,
coverage_threshold, witness_replay_threshold,
conclusive_rate_threshold,
required_capabilities, toolchain_fingerprint
```

The release manifest also carries `builtin_policy_hashes`, a map from each versioned built-in
policy ID to the SHA-256 of its canonical JCS bytes. For v3.1.x this includes
`builtin_bootstrap_v1`. The manifest hash commits to this map. The corresponding canonical
object is a release artifact, and the exact digest is published rather than recomputed from
implementation defaults at runtime; startup recomputes the digest from the embedded canonical
object and rejects a mismatch as `manifest_mismatch`.

`spec_core_hash` is the SHA-256 of the canonical encoding of every `CheckSpec` field **except**
`maturity`, `promotion_record_hash`, and `spec_core_hash` itself. It is the maturity-independent
identity of a specification, so the same specification can be validated for a target maturity
before its `maturity` field changes (§15.10). The `CheckSpec` hash listed in the manifest covers
all fields; a promoted spec therefore has a different full hash from its shadow predecessor, and
the manifest hash changes with it.

CI verifies the corpus hashes, thresholds, maturity, and toolchain fingerprint on every release
run. A behavior change without a corpus update is a release failure. The release manifest may
list any subset of checks. `release_summary` has four fields: `blocking[]` is exactly the set of
checks at maturity `provisional` or `stable`; `shadow[]` is the set at maturity `shadow`;
`maturity{}` maps every shipped check ID to its maturity; `not_shipped[]` lists registered
checks absent from the manifest. The PASS text (§1.3) is generated from this summary.

## 13. Execution, budgets, sandboxing, and determinism

### 13.1 Execution model

- v3.x runs checks sequentially in fixed registry order; shadow checks run after all blocking checks, under their own budgets, and are skipped with a `not_executed` notification if the run deadline has already been reached.
- File-fact computation may use a bounded worker pool. Worker count is a performance
  parameter, never a semantic input.
- Facts are requested through `FactProvider`; checks receive facts only.
- Z3 is imported lazily and only when a semantic candidate exists.
- The verification core never accesses the network or executes repository code (§1.4).
- Default deadlines: 60 seconds cold, 10 seconds warm, on the reference workload.

### 13.2 Budgets

Budgets are deterministic operation counts and size caps, not wall-clock allowances:

- maximum entities and references per check;
- maximum symbolic paths per function;
- maximum taint iterations and depth;
- maximum solver `rlimit`;
- maximum facts per check;
- maximum file bytes, AST depth, and node count per parsed file (`parse_resource_limit`).

Budgets are assigned per check and per relevant scope before execution. Checks cannot consume
each other's budget. No shared mutable semantic state exists between checks. The fact cache is
shared immutable storage, not shared semantic state (§14). Cache hits may avoid recomputing
validated immutable facts, but may not skip a check, reduce its required scope, alter coverage,
increase a deterministic budget, or substitute a cached aggregate verdict.

A wall-clock watchdog and OS memory/CPU limits are operational interruption safeguards, not
semantic budgets. If one interrupts required work before the check completes:

- an existing validated finding remains visible and blocking; the check outcome is `FAIL`
  unless the check also faults, in which case §5.2 applies;
- otherwise the affected blocking check is `INCONCLUSIVE` (`watchdog_interrupted`);
- the affected blocking check's coverage is `PARTIAL` or `UNKNOWN`;
- the interruption never creates `PASS` or a defect.

A cache hit may allow required deterministic work to complete before the watchdog, but a faster
completion is not itself evidence of correctness: the same deterministic budgets, scope,
coverage requirements, and evidence validation still apply. The parity guarantee is for
completed runs with identical logical inputs and deterministic budgets. A watchdog-interrupted
run is incomplete and is not a completed run for the parity claim. Release tests must separately
verify deterministic-budget equivalence, completed-run cache parity, and watchdog behavior.

Solver random seeds and configuration are pinned and included in the toolchain fingerprint.
Scheduler reduction order is stable regardless of completion order.

### 13.3 Determinism scope

> Identical logical inputs (including `as_of_date`), policy, toolchain, and deterministic
> analysis budgets produce byte-identical canonical payloads for completed executions.
> Resource exhaustion may produce INCONCLUSIVE and must never produce PASS.

Caching must not change the result of a completed execution under the same deterministic
budgets. Cache parity compares completed runs; a run interrupted by a wall-clock watchdog is
incomplete and is evaluated under §13.2, not treated as a completed parity sample. A cached
run may finish before a watchdog only when cache reuse avoids recomputing immutable facts;
all required checks, deterministic budgets, coverage conditions, and evidence validation must
still complete. The watchdog cannot be used as a substitute for deterministic work limits, and
cache hits cannot suppress a required analysis step or convert incomplete coverage into
`COMPLETE`.

### 13.4 Sandboxed workers

PR content is hostile input. `ast.parse`, tree-sitter, and Z3 can exhaust memory, recursion,
or time on adversarial files. Therefore:

- Frontends and the solver run in **separate child processes** with a cleared environment, no
  credentials, no network, and resource limits (address space, CPU time, recursion depth; POSIX
  `rlimit`s, Windows Job Objects), exchanging length-prefixed canonical JSON.
- Deterministic size/depth caps are enforced inside the worker (`parse_resource_limit`);
  OS-level kills map to `watchdog_interrupted`; an unexplained worker crash or protocol
  violation maps to `ERROR` (`internal_fault`) for the affected check and never crashes the
  gate. Findings established before the fault are preserved (§5.2).
- Worker results are validated structurally before use.

## 14. Cache model and trust boundary

### 14.1 Location

The default cache lives in the repository's administrative directory:

```text
<git-common-dir>/verifyci-cache/v3/
```

or a dedicated local cache directory outside the working tree. It is never stored in a
tracked or PR-controlled path. An explicit `--cache-dir` that resolves inside the working
tree is rejected with `ERROR` (`invalid_cache_location`).

### 14.2 Modes

| Mode | Where | Authentication | Negative results cached |
|---|---|---|---|
| `authenticated` | Trusted CI contexts only, including a PR run only when its required workflow is defined outside PR control and the key remains isolated | HMAC-SHA256 over entry digest and key, key from a secret available only to trusted workflows | Yes |
| `none` | Fork PRs, PR-controlled workflow definitions, `pull_request_target`-style untrusted contexts, or any CI context without a valid protected key | n/a; no cache reads or writes | n/a |
| `local` | Developer machines only; requires `--allow-local-cache`; never used by the Action | None; trust domain is the local user (directory mode `0700`) | **No** |

**Authoritative results.** Only runs in mode `authenticated` or `none` yield an authoritative
gate result. A `local`-mode run is a developer pre-flight: its envelope carries
`cache.authoritative: false`, the CLI states that the result is non-authoritative, and the
Action refuses `local` mode. An unauthenticated entry never influences an authoritative
verdict.

A digest alone proves an entry is self-consistent, not authentic; a poisoned cached `UNSAT`,
"no taint path", or VFIR could otherwise silently suppress a finding, and replay validation
cannot catch it because replay checks only positive witnesses. Hence the rules below.

### 14.3 Entries and validation

- Entries are immutable, sharded, and written atomically (temporary file + rename).
- Every entry is addressed by the exact key schema of §14.3.1, which partitions facts into Tier 1 (file-local) and Tier 2 (closure-scoped) so that cross-file edits never serve stale interprocedural facts.
- Each entry carries a content digest, toolchain fingerprint, and (in `authenticated` mode) an
  HMAC.
- Malformed, stale, mismatched, unauthenticated-in-authenticated-mode, or unverifiable
  entries are cache misses.
- **Negative-capable entries** (solver `UNSAT`, refuted candidates, taint summaries asserting
  no path, any fact that encodes an absence) are written and trusted **only in `authenticated`
  mode**. In `local` mode they are recomputed.
- The allowed cached object types are exactly `entity_spans`, `symbol_facts`, `vfir`, `summary`,
  `contract_binding`, `semantic_formula`, and `solver_result` from §14.3.1. The aggregate verdict,
  secret-scan results, and standalone deletion-reachability results are never cached.
- Facts are derived from Git blobs, never the working tree. A cache miss falls back to
  authoritative Git bytes.
- **Deterministic sampled recomputation:** a release-pinned sampling policy selects cache
  entries by `SHA-256(UTF8("verifyci-cache-sample-v1") || 0x00 || ASCII(entry_key_hex))`, where
  `entry_key_hex` is the lowercase 64-character hexadecimal encoding of the entry key digest.
  Interpret the resulting digest as an unsigned 256-bit big-endian integer and select the entry
  iff that integer is less than `floor(5 * 2^256 / 100)`. The initial sample rate is exactly 5/100;
  integer arithmetic is normative. Both the algorithm version and rate are part of the release
  manifest/toolchain fingerprint and cannot be changed at runtime.
  Selection is per entry key, not per value digest, process, worker, or wall-clock time, so the
  same key is selected on every run under the same release configuration. Every selected hit
  requested by the run is recomputed from authoritative Git-derived inputs before its cached
  value may be consumed. Results from concurrent validations are collected and serialized in
  sorted entry-key order. Any mismatch yields `ERROR` (`cache_integrity_mismatch`), reports the
  sorted mismatching entry keys (or their redacted digests), and disables cache reads for the
  remainder of the run. Sampling selection and mismatch reporting are deterministic; a detected
  mismatch intentionally changes the verdict to `ERROR` rather than preserving a cached verdict.
- The cache cannot override coverage, budgets, policy, or verdict logic.

#### 14.3.1 Key schema (normative)

**Notation.** Key components are canonical JSON (RFC 8785). An entry key is
`SHA-256(object_type ‖ 0x00 ‖ canonical(components))`. `TC` is the toolchain fingerprint, `CSV`
the cache schema version, and `rev` is `base` (merge base) or `head`. Blobs, not commit IDs,
identify content, so entries are reusable across PRs. `T1(file, rev)` is the Tier 1 key of a
file at a revision.

**Policy digests.** No entry is keyed by the whole-policy hash. `pd_x` is the SHA-256 of the
canonical JSON of only the named **authoritative** policy sections after normalization; the
proposed policy never enters a key (§8.3), and waivers, acceptances, `[gate]`, and secret
sections never enter any fact key. `pd_paths` = `[paths].source_roots`; `pd_public` = `[public_api]` and `[entrypoints]`;
`pd_decor` = `[decorators.transparent]`; `pd_calls` = `[calls.models]`; `pd_guard` =
`[protected_guards]` and `[protected_errors]`; `pd_taint` = `[taint]` and `[forbidden_calls]`.

**Closure digest** `closure_digest(e, rev, κ)` for entity `e`, where `κ` is `callees`
(transitive resolved callees) or `callers+callees` (one hop in each direction):

1. Membership is computed from resolved call and import edges only, to the pinned
   deterministic depth bound `closure_depth`, which is part of the budget digest.
2. Each member `m` contributes a leaf record `{qname, T1(file(m), rev), interface_digest(m)}`.
   `interface_digest` is the digest of `m`'s signature and, for callee members of a `callees`
   closure, of `m`'s Tier 2 `summary` digest.
3. Each edge that cannot be resolved contributes `{site_digest, reason_code}`, so a change in
   resolvability alters the key. Each import or call resolution contributes its **resolver probe
   list**, the ordered `(path, blob_hash | absent)` pairs the resolver consulted, so adding a
   file that would newly resolve or shadow an import also alters the key. The list includes every
   intermediate module or barrel/re-export file traversed or consulted while resolving a symbol,
   even when the final caller and target blobs are unchanged. Examples include Python package
   `__init__.py` files and their `__all__` exports, TypeScript/JavaScript `index.ts` or `index.js`
   files, `export * from` chains, and package-resolution metadata that the pinned resolver reads.
   Both present and absent candidates are recorded in deterministic probe order; a change to any
   intermediate probe changes the closure digest.
4. Members of a strongly connected component are keyed jointly. Their leaf records exclude each
   other's summary digests and include the sorted T1 keys of all component members. The fixpoint
   starts from a pinned bottom value and iterates within the deterministic iteration budget; the
   result of a run that hit the budget is not cached.
5. `closure_digest` is the SHA-256 of the canonical encoding of the records of items 2–3, sorted
   by `(qname, T1)`.

| Object | Tier | Key components | Negative-capable |
|---|---|---|---|
| `entity_spans`, `symbol_facts` | 1 | `CSV, TC, blob_hash, repo_relative_path, language_id, frontend_version, pd_paths` | no |
| `vfir` (policy-independent lowering; guard edges, decorator transparency, and call models are applied at analysis time) | 1 | Tier 1 components + `lowering_version` | no |
| `summary` (effect/taint summary of one entity at one revision) | 2 | `CSV, TC, T1(file(e), rev), qname(e), closure_digest(e, rev, callees), pd_decor, pd_calls, pd_taint, budget_digest` | yes (no-path summaries) |
| `contract_binding` (signature and call-site compatibility of one changed entity) | 2 | `CSV, TC, T1(base), T1(head), qname_base(e), qname_head(e), closure_digest(e, base, callers+callees), closure_digest(e, head, callers+callees), pd_public, pd_decor, pd_calls, budget_digest` | yes (no incompatibility) |
| `semantic_formula` with `formula_kind=guard` (aligned `Φ` formulas for a protected effect pair, §8.4.2.1) | 2 | `CSV, TC, formula_kind, T1(base), T1(head), entity pair, closure_digest(e, base, callees), closure_digest(e, head, callees), alignment_digest, pd_decor, pd_calls, pd_guard, budget_digest` | no |
| `semantic_formula` with `formula_kind=exception` (aligned uncaught-exception formulas, §8.4.2.2(a)) | 2 | `CSV, TC, formula_kind, T1(base), T1(head), entity/exception pair, closure_digest(e, base, callees), closure_digest(e, head, callees), alignment_digest, pd_decor, pd_calls, pd_guard, budget_digest` | no |
| `semantic_formula` with `formula_kind=binding_swap` (call-argument or tuple-return swap, §8.4.2.2(b)) | 2 | `CSV, TC, formula_kind, T1(base), T1(head), entity/site pair, closure_digest(e, base, callers+callees), closure_digest(e, head, callers+callees), alignment_digest, pd_public, pd_decor, pd_calls, pd_guard, budget_digest` | no |
| `solver_result` | 2 | the `semantic_formula` key + `solver_digest` (solver version, pinned seed and configuration, `rlimit`) | `UNSAT` yes; `SAT` no; `UNKNOWN` never cached |

`alignment_digest` is the digest of the alignment tables appropriate to the formula kind:
§8.4.2.1(c) for guards and §8.4.2.2 for exception/binding formulas; `budget_digest` is the digest
of the deterministic budgets relevant to the object. The `formula_kind` is mandatory and is part
of the canonical key. A formula implementation may not use the guard key for exception or
binding-swap formulas.

`contract_binding` includes `pd_calls` conservatively because a declared call model can affect
how a resolved call site's modeled behavior and binding evidence is interpreted by composite
contract analysis. This may invalidate some signature-only cache entries when `[calls.models]`
changes, but it avoids relying on an implicit claim that the model cannot affect the check. The
invalidation is intentional and is covered by a contract-binding cache test.

For `formula_kind=binding_swap`, both-revision `callers+callees` closure digests are mandatory:
call-site/tuple-return findings can depend on caller compensation as well as the changed entity's
callees. `pd_public` is mandatory because `[public_api]` and `[entrypoints]` alter the contract
against which a return-swap is evaluated. `pd_decor`, `pd_calls`, and `pd_guard` are included
because decorator behavior, modeled call results, or modeled guard behavior can affect the
aligned site and its reachability witness. Omitting any required component is an invalid cache
schema and must be rejected, not silently downgraded to a weaker key.

**Diff-dependent objects bind both revisions**: no object that compares base and head is keyed
by one revision alone. Results produced under budget exhaustion or watchdog interruption are
never cached. Secret-scan results and aggregate verdicts are never cached.

**Deletion reachability is not a cache object in v3.1.x.** The reachability walk is recomputed
from the current authoritative entrypoint/public-API roots and current reference edges each run;
only policy-independent primitive symbol/reference facts may be reused. No standalone cached
`deletion_reachability` verdict or summary is permitted. If a future spec adds one, its key must
include `pd_public`, both revisions where the result is diff-dependent, and the full resolver
probe/closure digest; an implementation must reject that object type until its schema is
specified.

**Authentication binds the key.** In `authenticated` mode the HMAC covers
`(key_id, object_type, canonical key components, value digest)`, so a valid entry cannot be
replayed under another key, object type, or namespace.

**Artifact bucket versus entry key.** The CI cache artifact identifier (for example a GitHub
Actions cache key) is `(repository, key_id, TC, CSV)` only and carries no policy or content
digest; the per-entry keys above govern reuse.

### 14.4 GitHub Actions cache rules

- Restore caches only from trusted branches or trusted workflow runs, and only into workflows
  that hold the cache key.
- A same-repository PR run may read authenticated cache entries only when the required workflow
  definition and Action invocation are outside PR control, the key is withheld from all
  PR-controlled steps and workers, and the cache namespace is repository-confidential. Such
  PR runs are read-only and never write.
- Fork PRs, PR-controlled workflow definitions, and `pull_request_target`-style untrusted
  contexts use mode `none`: no cache reads, no cache writes, and no cache key.
- Do not restore a cache produced by an untrusted fork or `pull_request_target` workflow into
  a privileged workflow.
- Treat cache artifacts as repository-confidential; scope them to the repository's trusted CI
  workflows and branches.
- Entry keys include the toolchain fingerprint and the per-object-type policy digests of §14.3.1, and the artifact bucket key follows §14.3.1; no entry is keyed by the whole-policy hash.
- Treat any cache artifact as untrusted input: validate structure, digests, HMAC, and
  fingerprints; fall back to Git on any mismatch.

### 14.5 Cache parity and uncached audit

Release validation requires cached and uncached executions to produce identical verdicts
and canonical payloads when the cache entries are valid/authentic and both executions complete
under the same deterministic analysis budgets and release/toolchain configuration. Cache
sampling configuration is release-pinned, and selected-entry membership is deterministic.
Watchdog behavior is tested separately and is not part of the parity claim.

A deliberately detected cache-integrity mismatch is an exception to parity: the cached run must
fail closed with `ERROR` (`cache_integrity_mismatch`), while an uncached run recomputes from
source inputs and need not have the same verdict. Such a mismatch is tested as a separate
integrity-detection case, not counted as a cache-parity failure. A **scheduled uncached audit**
(for example nightly, on the default branch and a sample of recently merged PR ranges) runs with
`--no-cache` and compares payloads for valid-cache runs; a divergence is a security incident
and invalidates the cache namespace.

### 14.6 Key provisioning and trust model

An HMAC proves authenticity only if the signing key is out of reach of the party able to
modify the cache. Therefore:

1. **Provisioning.** The key is 32 random bytes, generated per repository cache namespace and
   stored as a CI secret in the trusted environment (the secret scope of the required workflow
   or protected-branch environment, §8.6). It is never stored in the repository, the cache, a
   bundle, or logs.
2. **Isolation.** The key is never provided to workflows triggered from forks, to
   `pull_request_target`-style untrusted contexts, or to any workflow whose definition the PR
   can modify. The gate reads the key at startup in the parent process, removes it from the
   environment before spawning any worker, and never passes it to sandboxed workers (§13.4).
   Repository code is never executed, so the key is exposed only to VerifyCI's own code.
3. **Namespace ownership.** A cache namespace is `(repository identity, key ID, toolchain
   fingerprint)`. Entries record the key ID, not the key. Only trusted workflows own and write
   a namespace.
4. **Read/write rule.** PR event type alone does not establish trust. A same-repository PR
   may open the cache read-only only through the externally required workflow described in
   §8.6, when the workflow definition is not PR-controlled and the key is withheld from
   PR-controlled steps and workers. Fork PRs, PR-controlled workflow definitions, and
   `pull_request_target`-style untrusted contexts use mode `none` and perform no cache access.
   Only trusted runs (protected target-branch refs and trusted merge-candidate runs) write
   entries. PR-changed blobs are not pre-populated by the PR run; cache misses fall back to
   authoritative Git bytes and recomputation.
5. **Rotation.** Rotate at least every 90 days and immediately on suspected exposure. A new
   key ID starts an empty namespace; entries under any other key ID are misses. On suspected
   compromise: rotate, discard the old namespace, and run an uncached audit (§14.5).
6. **Key unavailable.** If no key is provisioned, the key is malformed, or the context is
   untrusted, the cache mode is `none`: no cache reads or writes. This affects latency only,
   never the verdict; the envelope records `cache.mode: none` and the reason. The Action never
   falls back to `local` mode.
7. **Trust boundary.** An entry with a bad HMAC, an unknown key ID, or a wrong namespace is a
   cache miss. A confirmed mismatch from sampled recomputation is `ERROR`
   (`cache_integrity_mismatch`) and bypasses the cache for the rest of the run.

Confidentiality of the key is a stated assumption: `cache_key_isolation_not_verified` (§8.6).

### 15.4 Check corpora, statistics, and maturity

Each check owns frozen corpora of small bare Git repositories with hand-authored labels for
outcome, coverage, reason codes, and findings. Labels are authored from this specification,
never generated by the engine. A case is never edited after it has been run against the
engine; a change is a new case ID, and the corpus hash covers the full history.

**Why point thresholds were insufficient.** "Recall $\ge 0.95$" on a 20-case corpus proves
little: 19/20 has a one-sided 95% lower confidence bound near 0.75. And precision 1.0 on cases
written by the same author who wrote the checker is nearly tautological. v3.1 therefore
requires:

1. **Minimum corpus size per defect ID** and reporting of the one-sided 95% Clopper–Pearson
   **lower bound** on recall, not the point estimate. With zero misses over $n$ positives the
   bound is $0.05^{1/n}$: $n = 30$ gives $\approx 0.905$; $n = 59$ gives $\approx 0.951$. With $k$ misses, $n$
   must be raised until the computed lower bound meets the threshold.
2. **Negative cases** at the same minimum per defect ID, with the upper bound on the
   false-blocking rate reported the same way.
3. **Held-out set:** at least 25% of every corpus is authored by a second labeller working from
   this specification, kept out of the check author's working set until the release run.
4. **Mined set:** at least 200 merged pull requests from at least 5 open-source repositories
   (Python and TS/JS), including revert commits and security-fix reversals. Every blocking
   finding on it is adjudicated by two reviewers. This estimates field precision and the
   conclusive rate.

**Maturity levels** (*initial* thresholds):

| Maturity | Verdict effect | Evidence required |
|---|---|---|
| `shadow` | None (advisory annotations only) | Contract and invariant tests; corpus runs reported without thresholds; mined-set run reported |
| `provisional` | Blocking | $\ge 30$ positives and $\ge 30$ negatives per defect ID; recall lower bound $\ge 0.90$; **zero** false blocking findings on all corpora **and** on adjudicated mined findings; coverage agreement 1.0; witness replay 1.0; redaction 1.0; conclusive rate on mined set $\ge 0.80$ |
| `stable` | Blocking | $\ge 59$ positives and $\ge 59$ negatives per defect ID; recall lower bound $\ge 0.95$; zero false blocking findings on all corpora and mined set; coverage agreement 1.0; witness replay 1.0; redaction 1.0; conclusive rate $\ge 0.90$ |

Common to all blocking maturities: deterministic payload across repeated runs and worker
counts; witness replay 1.0 for every blocking finding, including one preserved under `ERROR`.
Grounding's hand-labelled provenance and coverage classification must agree 100%.

### 15.10 Evidence artifacts and the promotion prohibition

This document does not assert that the datasets, reviewers, or measurement pipeline required
by §15.4 exist. They are release prerequisites that must be produced.

**Versioning.**

- *Corpora:* each case is a directory with `case.json` (case ID, defect ID or none, labels,
  labeller role `author` or `second`, authored date, specification section cited) and a bare
  repository or Git bundle. The corpus hash is SHA-256 over the sorted case hashes; every
  historical corpus hash is retained. Cases are immutable after their first engine run.
- *Mined set:* `mined/index.json` lists repository URL, license, pinned commit SHAs, and a
  snapshot hash; the set is reproducible from the pinned SHAs.
- *Adjudication records:* one record per blocking finding on the mined set, with finding
  identity, two reviewer role identifiers, each reviewer's verdict (`true_positive`,
  `false_positive`, or `undetermined`), rationale, and timestamps. A disagreement goes to a
  third reviewer. `undetermined` counts as a false positive for promotion.
- *Measurement:* a single pinned command, `release-validate`, computes per-check counts,
  Clopper–Pearson bounds, conclusive rate, cache-parity results, and corpus hashes from these
  artifacts and emits `release_report.json`, reproducible from the tagged commit and listing
  every input hash.

**Promotion sequence (normative).** Promotion is a four-step sequence in which each artifact
references only artifacts created before it, so no hash cycle exists.

1. **Candidate.** The author freezes a candidate `CheckSpec`, computes its `spec_core_hash`
   (§11.8), and declares `target_maturity` (`provisional` or `stable`). The candidate's
   `maturity` field remains `shadow`.
2. **Validation.** `release-validate` runs against the candidate and emits
   `release_report.json`, which records `spec_core_hash`, `target_maturity`, the toolchain
   fingerprint, every corpus, held-out, mined-set, and adjudication input hash, the
   measurement-command identity, and per-requirement results for `target_maturity`. It contains
   no reference to the promotion record or the manifest.
3. **Record.** An immutable `promotion_record.json` is created containing `spec_core_hash`,
   `target_maturity`, `report_hash` (SHA-256 of the exact `release_report.json` bytes), the
   toolchain fingerprint, and the creation date. It contains no reference to the manifest.
4. **Manifest.** The manifest's `CheckSpec` entry sets `maturity = target_maturity` and
   `promotion_record_hash` to the SHA-256 of the record bytes; the manifest hash covers these
   entries.

CI verifies the chain as one unit: recompute `spec_core_hash` from the manifest entry
(excluding `maturity`, `promotion_record_hash`, and itself) and require it to equal the
record's; require the record's `target_maturity` to equal the entry's `maturity`; require the
record's `report_hash` to equal the hash of the report; require the report to carry the same
`spec_core_hash`, target maturity, and toolchain fingerprint and to show every requirement of
that maturity met; and require the toolchain fingerprint to equal the build's. Any mismatch
fails the build with `check_not_validated`. A change to any spec-core field (thresholds, corpus
hashes, defect semantics versions, capabilities, and so on) changes `spec_core_hash` and
invalidates the record. Demotion to `shadow` needs no record.

**Promotion prohibition.**

- A `CheckSpec` may carry a maturity above `shadow` only when a valid `promotion_record.json`
  binds its exact `spec_core_hash` and target maturity to a `release_report.json` showing every requirement
  of that maturity met. CI verifies both hashes and all thresholds; otherwise the build fails
  with `check_not_validated`.
- If any required artifact is absent — an empty held-out set, no second labeller, a missing
  adjudication record — the requirement is unmet and the check remains `shadow`. Thresholds are
  never waived, and no check is promoted on projected or partial evidence.
- The second labeller and adjudicators must be different people from the check's author(s),
  recorded by role identifier.

Development versus release:

- Internal development builds may exercise individual checks and corpora for diagnostics.

  the capabilities used, and all invariants and performance gates pass. The PASS text and

- Any change to a check, its corpus, the relevant toolchain, or supported semantics
  invalidates the applicable release approval until release validation completes again.

## 18. Acceptance criteria for v3.1

VerifyCI v3.1 is not complete until all of the following are established by artifacts:

- [ ] Every shipped check is registered with an immutable `CheckSpec` at a declared maturity.
- [ ] Every blocking check meets its maturity's corpus, lower-bound, held-out, mined-set,
      coverage, witness-replay, and conclusive-rate thresholds.
- [ ] Frontend conformance and differential-fidelity suites pass for every supported
      construct used by evidence at blocking maturity.
- [ ] Invariant and adversarial suites pass, including fail-closed, cache, policy, Git
      hardening, sandbox, and manifest cases.
- [ ] A finding preserved under a later check error remains visible, aggregates `ERROR`, and
      sets `blocking_findings_present`.
- [ ] Policy-change review triggers only for PR-authored changes (including onboarding bootstrap);
      target-branch advancement alone does not trigger review.
- [ ] A `.verifyci/policy.toml` change always records both `policy_change_review` and `gate_integrity_review` before validating proposed contents. This remains true for deletion, onboarding bootstrap, and malformed/schema-invalid proposals; on invalid proposals, `invalid_policy` appears in `verdict.fault_reason_codes[]`, both review codes remain in `verdict.reason_codes[]`, and aggregate verdict/exit code are `ERROR`/3. Policy-only S1 and combined policy/gate-control changes are tested for exact reason-code sets.
- [ ] Expired or not-yet-effective authoritative waivers and coverage acceptances are evaluated on match and remain ineffective; unrelated policy edits do not become `invalid_policy` merely because an unchanged authoritative record has `created > as_of_date`. The `created <= as_of_date` proposed-entry constraint applies only to records newly added or semantically modified against the authoritative record with the same stable policy ID (record namespace plus exact TOML table key), comparing every normalized schema field except the table key and not the waiver finding fingerprint; renaming an ID is remove-plus-add (all entries are new during onboarding bootstrap). Waivers and acceptances enforce `created <= as_of_date <= expires` when active; coverage acceptances additionally enforce `0 <= expires - created <= 180` days.
- [ ] Gate-integrity changes yield `REVIEW` and cannot be excluded or waived; `CODEOWNERS` ownership coverage is decided by the §8.6.1 rule (active-file precedence, covering rule, non-interference, restricted syntax subset) and validated on the §8.6.1 corpus, including paths added by later PRs.
- [ ] `deny_changes` path and symbol rules are defined, evaluated by grounding, and
      corpus-validated; doc-only edits do not make grounding inconclusive; `diff-tree -r -l2000`
      and `rename_limit_exceeded` behave deterministically, with coverage downgraded only when a required mapping is affected.
- [ ] The §8.3.1 remediation scenarios S1–S4 are regression-tested: policy-only remediation reaches `REVIEW` (exit 4) and clears under `review-mode: codeowners` only when the proposed policy contains no expired waiver/acceptance and no separate blocker; expired entries retained in the proposal prevent clearing; a combined policy-and-code PR never becomes successful by renewing a waiver or acceptance.

- [ ] Tier 2 resolver probe lists include intermediate package and barrel/re-export files (`__init__.py`, `__all__`, `index.ts`/`index.js`, `export * from`, and consulted package metadata); changes to any probe invalidate the affected closure digest.
- [ ] Every frontend entity declares `entity_status` (`LOWERED`, `PARTIAL`, or `OPAQUE`); checks requiring unavailable capabilities cannot claim `COMPLETE` coverage, while provenance-only checks remain independently evaluable.
- [ ] Runtime expiry-review routing applies to schema-valid expired waiver/acceptance entries; missing, empty, wrongly typed, or malformed required authorization fields in authoritative or proposed policies produce `ERROR` (`invalid_policy`).
- [ ] `SEM-GUARD-*` detection follows §8.4.2.1 (shared-vocabulary and guard-site alignment, `L_base(E)`, path-condition predicate Δ, bypass/abort versus same-polarity weakening classification), is replay-validated, catches `try/except: pass` swallowing and polarity inversion, classifies `>` to `>=` boundary changes as weakening when the paired guard remains, and reports alignment failures as `semantic_alignment_unresolved` rather than as findings.
